# Style Guide для лабораторных по АСД

Этот документ описывает требования к стилю кода, именованию и оформлению коммитов для курса АСД.

> Примеры приведены для Java 17 + Maven + JUnit 5. Для другого стека правила именования и коммитов остаются те же, отличаются только инструменты.

---

## Язык и стек

| Компонент       | Значение                     |
|-----------------|------------------------------|
| Язык            | Java 21+                     |
| Сборка          | Maven                        |
| Тестирование    | JUnit 5                      |
| Форматирование  | Google Java Style / Spotless |
| Линтер          | Checkstyle                   |

---

## Именование

| Элемент            | Стиль            | Пример                          |
|--------------------|------------------|---------------------------------|
| Классы             | `PascalCase`     | `BinarySearchTree`              |
| Интерфейсы         | `PascalCase`     | `PriorityQueue`                 |
| Методы             | `camelCase`      | `insert`, `removeMin`, `bfs`     |
| Поля и переменные  | `camelCase`      | `currentNode`, `maxDepth`       |
| Константы          | `UPPER_SNAKE`    | `MAX_CAPACITY`, `DEFAULT_LOAD`  |
| Пакеты             | строчные         | `ru.university.acsd.lab01`      |

---

## Структура кода

- Каждый класс — в отдельном файле.
- Имя файла должно совпадать с именем публичного класса.
- В начале файла — короткий Javadoc с назначением класса и ключевыми особенностями.
- Импорты упорядочены, **wildcard-импорты запрещены** (`import java.util.*`).

---

## Стиль и читаемость

- Длина строки: **не более 120 символов**.
- Отступы: **4 пробела** (табуляция запрещена).
- Избегайте «магических» чисел — вынесите в константы или добавьте комментарий с обоснованием.
- Методы должны быть компактными (желательно **≤ 30 строк**). Если метод длинный — разбейте на вспомогательные.
- Дублирование кода недопустимо — общие фрагменты вынесите в отдельные методы / классы.

---

## Комментарии и документация

- Javadoc обязателен для публичных классов и методов.
- Для нетривиальных алгоритмов добавьте комментарии с пояснением идеи и граничных случаев.
- Не пишите комментарии, которые повторяют код («увеличиваем счётчик»).

---

## Тесты

- Названия тестов: `should_verb_description` — например, `shouldReturnNullWhenTreeIsEmpty`.
- Тесты должны быть независимыми (без общих статических состояний).
- Используйте понятные имена переменных внутри тестов (`expected`, `actual`, `root`).

---

## Коммиты и Git

### Формат сообщения коммита

```
<тип>: <тема>
```

| Тип       | Когда использовать                              |
|-----------|-------------------------------------------------|
| `feat`    | Новая функциональность / реализация алгоритма   |
| `fix`     | Исправление ошибки                              |
| `refactor`| Рефакторинг без изменения поведения            |
| `test`    | Добавление или исправление тестов              |
| `docs`    | Изменение документации                          |

**Примеры:**

```
feat: implement binary search tree insert
fix: handle null input in graph traversal
test: add edge cases for array list removal
```

### Правила

- Избегайте коммитов вида `fix`, `update`, `1`, `changes`.
- Коммит должен быть **атомарным**: одна логическая задача — один коммит.
- Перед отправкой PR сделайте `rebase` на `main` и убедитесь, что история коммитов чистая.

---

## CI и сборка

- Не отключайте проверки линтера и тестов.
- Если тесты падают — сначала исправьте ошибки, затем отправляйте PR.
- Убедитесь, что проект собирается локально (`mvn clean test`) перед отправкой.

---

## Запрещённые практики

- Хардкод ответов и «обман» тестов.
- Копирование кода у других студентов.
- Использование готовых реализаций структур данных из сторонних библиотек (если не разрешено условием).
