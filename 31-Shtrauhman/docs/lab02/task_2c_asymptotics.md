# Задача 2C. `CollisionKey` в `HashMapCustom` — асимптотика

У всех ключей `hashCode() = 42`, поэтому стартовая ячейка одна и та же: h = 42 % m. Линейное пробирование
укладывает ключи подряд, начиная с h (с переходом через конец массива), — получается одна цепочка длины n.
Равномерного хеширования больше нет, и оценки O(1) из задачи 2A перестают действовать.

## Время операций

Пусть ключ, вставленный i-м по счёту (i = 1..n), лежит на i-й позиции цепочки (так и есть без удалений).

| Операция | Проверено ячеек | Сравнений `equals` |
|---|---|---|
| `get` / `containsKey` / `remove` для i-го ключа | i | i |
| `get` отсутствующего ключа | n + 1 | n |
| `put` нового ключа при k ключах в таблице | (k + 1) на поиск + (k + 1) на вставку | k |

Отсюда:

- n вставок: Σ (2k + 2) для k = 0..n−1 = n² + n = **Θ(n²)**, в среднем **Θ(n)** на одну вставку;
- n поисков всех ключей: Σ i = n(n + 1) / 2 = **Θ(n²)**;
- перехеширование при s ключах переносит их по одному в одну цепочку: s(s − 1) / 2 проверок. Размеры s при
  удвоениях образуют геометрическую прогрессию 12, 24, …, поэтому суммарно это не больше (4/3) · s²_max / 2 = O(n²)
  и порядок не меняет.

Для n = 10 000: около 10⁸ проверок ячеек на вставки и 5 · 10⁷ на поиски, тогда как с нормальными хешами — порядка
2.5 · 10⁴ (по 2.5 проверки на успешный поиск при α ≤ 0.75).

## Проверка по замерам

При квадратичной сложности рост n в 2 раза должен давать рост времени примерно в 4 раза.
По `benchmarks.md`: 5 000 → 10 000 ключей — 122 → 518 мс, ×4.3. На переходе 1 000 → 5 000 (теория ×25)
получилось ×22.5: на малом n чуть заметнее постоянные накладные расходы.

## Память

Не зависит от хешей: те же два массива, **O(n)**. Коллизии ухудшают только время.
