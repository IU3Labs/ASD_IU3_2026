## Задача 1A. `PriorityQueueCustom<T>`

**Идея.** Двоичная min-куча в массиве: дети узла `i` — `2i + 1` и `2i + 2`, родитель — `(i − 1) / 2`.
`add` кладёт элемент в конец и поднимает (`siftUp`), `poll` переносит последний элемент в корень и опускает
(`siftDown`), выбирая меньшего из детей. Элементы сравниваются по естественному порядку (`T extends Comparable`).

**Почему массив.** Куча — всегда полное дерево, поэтому хранится в массиве без пропусков: связи вычисляются
по индексу, не нужны объекты-узлы и ссылки. Расширение — удвоение ёмкости (амортизированная O(1)).

**Решения.**
- При сдвиге элемент не меняется местами на каждом шаге, а держится в переменной и записывается один раз в конце —
  вдвое меньше записей в массив.
- После `poll` освободившаяся ячейка обнуляется, иначе массив удерживал бы ссылку на извлечённый объект.
- `peek` на пустой очереди, как и `poll`, бросает `NoSuchElementException` (в условии для `peek` поведение не задано,
  выбрано единообразие с `poll`). `null` не принимается — его нельзя сравнить.

**Асимптотика.** `add` — O(log n) амортизированно, `poll` — O(log n), `peek`, `size`, `isEmpty` — O(1); память O(n).

**Ручные тесты и зачем они нужны:**
- `[7 2 9 4 1 8 3] → 1 2 3 4 7 8 9` — главное требование: извлечение в порядке неубывания;
- дубликаты `[3 1 3 1 2]` — равные элементы не теряются и не мешают просеиванию;
- уже отсортированный и обратный вход — худшие случаи для `siftUp` (каждый новый элемент поднимается до корня);
- начальная ёмкость 1 и 100 элементов — проверка автоматического расширения;
- `Integer.MIN_VALUE` / `MAX_VALUE` — сравнение через `compareTo`, без вычитания, которое переполнилось бы;
- чередование `add` и `poll`, повторное использование после опустошения;
- пустая очередь: `poll` и `peek` → `NoSuchElementException`;
- 100 000 случайных операций сравниваются с `java.util.PriorityQueue` — проверка на большом объёме.

## Задача 2A. `HashMapCustom<K, V>`

**Идея.** Открытая адресация: ключи и значения в двух массивах, при коллизии — следующая ячейка
`(index + 1) % capacity`. Хеш-функция по условию: `Math.abs(key.hashCode()) % capacity`.

**Почему так.** Открытая адресация не создаёт объект на каждую пару (в отличие от цепочек), данные лежат в массиве
подряд. Цена — удаление: нельзя просто обнулить ячейку, иначе поиск остановится на «дыре» и не найдёт ключи,
вставленные дальше по цепочке. Поэтому удалённая ячейка помечается маркером `DELETED`: поиск через него проходит,
а вставка может занять его снова.

**Решения.**
- Загрузка считается вместе с маркерами `DELETED` и не превышает 0.75 — так в массиве всегда есть пустая ячейка,
  и цикл пробирования гарантированно заканчивается.
- Если порог превышен в основном маркерами, а живых ключей меньше половины порога, таблица перехешируется в ту же
  ёмкость (маркеры исчезают); иначе ёмкость удваивается. Без этого ёмкость росла бы при чередовании `put`/`remove`.
- Особый случай хеш-функции: `Math.abs(Integer.MIN_VALUE)` остаётся отрицательным, к остатку прибавляется `capacity`.
- Ключ `null` запрещён (у него нет `hashCode`), значение `null` разрешено — `containsKey` отличает его от отсутствия.

**Асимптотика.** `put`, `get`, `containsKey`, `remove` — O(1) в среднем (до 2.5 проверок на успешный поиск и 8.5
на неуспешный при загрузке 0.75), O(n) в худшем случае; `size`, `capacity` — O(1); память O(n).

**Ручные тесты и зачем они нужны:**
- ключи `1, 17, 33` при ёмкости 16 попадают в одну ячейку; удаление `17` не должно потерять `33` — главная проверка
  маркера `DELETED`;
- удалён ключ в начале цепочки, затем `put` существующего ключа дальше по цепочке — не должно появиться дубля;
- 12 ключей при ёмкости 16 — ёмкость 16, 13-й — ёмкость 32 (ровно порог 0.75) и все ключи на месте;
- 10 000 вставок — загрузка ни разу не превышает 0.75;
- 10 000 циклов `put` + `remove` и «скользящее окно» из 11 ключей — ёмкость не растёт бесконечно;
- ключи `-7` и `Integer.MIN_VALUE` — отрицательные хеши и переполнение `Math.abs`;
- обновление значения, значение `null`, повторное удаление, `null`-ключ;
- 200 000 случайных `put` / `remove` / `get` сравниваются с `java.util.HashMap`.

## Задача 2C. `CollisionKey`

**Идея.** Обёртка над строкой: `hashCode()` всегда 42, `equals` сравнивает строки. Так все ключи получают одну
стартовую ячейку — худший случай для хеш-таблицы. Контракт `equals`/`hashCode` не нарушен: равные ключи имеют
равные хеши.

**Асимптотика.** Ключи выстраиваются в одну цепочку: каждая операция O(n), n вставок и n поисков — O(n²);
память O(n) (см. `task_2c_asymptotics.md`).

**Тесты:** 10 000 ключей — вставка без потерь, поиск каждого, отсутствующий ключ, обновление без дублей,
удаление всех ключей и каждого второго, повторная вставка после удаления; отдельно — свойства самого ключа
(одинаковый хеш, равенство по строке, `null`). Деградация показана замерами и объяснена в `README.md`.

## Задача 3C. `Distinct.distinct`

**Идея.** Один проход: `HashMapCustom` служит множеством уже встреченных элементов, результат — `ArrayList`,
куда элемент дописывается при первой встрече. Порядок первого вхождения сохраняется сам собой.

**Почему хеш-таблица.** Проверка «был ли элемент» за O(1) в среднем вместо O(u) при поиске по списку.
Значение в таблице не нужно, поэтому везде записывается общий `Boolean.TRUE` — новых объектов на элемент нет.
Таблица не принимает `null`-ключ, поэтому `null` во входе отслеживается отдельным флагом.

**Асимптотика.** Время O(n) в среднем (O(n · u) при сплошных коллизиях), память O(u).

**Сравнение с `LinkedHashSet`** (подробно — `benchmarks.md`): памяти выделяется в 1.5–1.7 раза меньше (нет узла
на каждый элемент), по времени `LinkedHashSet` на 50–100 тыс. элементов быстрее в 3.2–3.5 раза: у него один поиск
на элемент вместо двух, а ёмкость сразу подбирается под размер входа, без перехеширований.

**Ручные тесты и зачем они нужны:**
- `[3 1 3 2 1 4 2] → [3 1 2 4]` — основное требование про порядок первого вхождения;
- пустой список, один элемент, все одинаковые, все разные — граничные случаи;
- два разных объекта `String` с одним содержимым — сравнение по `equals`, а не по ссылке; в результат идёт первый;
- `[1 null 2 null 1] → [1 null 2]` — `null` оставлен один раз на своей позиции;
- входной список не изменяется, результат — новый объект;
- `CollisionKey` во входе — работа поверх таблицы с коллизиями;
- 100 000 случайных чисел сравниваются с `new ArrayList<>(new LinkedHashSet<>(input))`.
