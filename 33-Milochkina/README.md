# ЛР2 — очереди с приоритетом и хеш-таблицы

Решены 1A–1D, 2A–2D и 3A–3D. Реализации хранят данные в собственных массивах.
Стандартные конкретные коллекции используются только в тестах и бенчмарках.
Для требуемых сигнатур List и Map возвращаются представления только для чтения: AbstractList,
AbstractMap и AbstractSet служат адаптерами, без стандартных контейнеров для хранения данных.

| Операция | Время | Память |
|---|---|---|
| Очередь: add | O(log n) амортизированно; отдельный рост — O(n) | O(C) на массив ёмкости C |
| Очередь: poll | O(log n) | O(1) рабочей памяти |
| Очередь: peek, size, isEmpty | O(1) | O(1) |
| Очередь: remove | O(n) | O(1) |
| Очередь: построение из массива | O(n) | O(n) |
| Хеш-таблица: put | O(1) ожидаемо амортизированно; перехеширование отдельно | O(C) |
| Хеш-таблица: get, containsKey, remove | O(1) в среднем при равномерном хешировании, O(C) в худшем случае | O(1) |
| Хеш-таблица: size, capacity | O(1) | O(1) |
| Хеш-таблица: occupied, keyAt, valueAt | O(1) | O(1) |
| Top-K | O(n log(k + 1)) для k ≥ 1, при k = 0 — O(1) | O(k) |
| Частоты слов | O(L) в среднем для текста длины L, включая обработку символов и вычисление хешей | O(U + S) |
| Уникальные элементы | O(n) в среднем | O(n) |
| Скользящий минимум | O(n log(n + 1)) | O(n) |

Оценки предполагают постоянную стоимость сравнений обычных ключей и элементов,
если отдельно не учитывается обработка строк. Для частот слов U — число уникальных
слов, S — их суммарная длина. Для Map-результата get и containsKey делегируются собственной
таблице, size работает за O(1), полный проход по entrySet — O(C).
Размеры памяти включают результат, если он создаётся. Ёмкость таблиц и кучи не уменьшается при удалении.
В плохом случае перехеширование открытой таблицы с C ячейками и большим числом одинаковых хешей —
O(C²), поскольку вставки заново проходят цепочки проб.

## Идеи реализации

- Куча: после вставки просеивание вверх, после удаления последняя ячейка занимает освободившееся место.
  Если новое значение меньше родителя по компаратору, нужен подъём; иначе спуск. Heapify проходит
  внутренние узлы с конца к корню. Узлов, которые могут спуститься на h уровней, не больше n/2^h,
  поэтому суммарная работа составляет O(n).
- Таблица: начальный индекс — `abs((long) hashCode) % capacity`. Преобразование к long позволяет
  обработать Integer.MIN_VALUE. Маркер DELETED сохраняет путь поиска и повторно используется при вставке.
  Ёмкость удваивается при превышении порога активных записей. Накопившиеся маркеры при необходимости
  удаляются перехешированием без роста.
- Для квадратичного пробирования применяется смещение `i(i+1)/2` (c1 = c2 = 0,5, смещение всегда целое)
  при ёмкости C = 2^p. Если индексы двух проб i < j < C совпали, произведение
  `(j-i)(i+j+1)` должно делиться на 2C. Один множитель нечётный, а второй положителен и меньше 2C,
  поэтому совпадения невозможны. За C шагов посещаются все ячейки; поиск ограничен C пробами.
- Top-K хранит в min-heap только k кандидатов. При сдвиге окна минимум извлекается из кучи
  только если его индекс вышел из окна; один элемент добавляется и удаляется не более одного раза.
- Для частот слов обработка регистра использует Locale.ROOT, пунктуация разделяет слова.
  Уникальные элементы записываются в выходной массив при первом появлении ключа;
  для проверки уже встреченных ключей используется квадратичное пробирование.

## Коллизии

CollisionKey возвращает одинаковый хеш, а равенство определяется исходной строкой.
Проверены вставка, поиск и удаление 10 000 таких ключей в обоих режимах. Значения с одинаковым хешем
начинают с одной ячейки и идут по одной последовательности: в замере в среднем требуется
5 000,5 пробы на успешный поиск вместо примерно 1–2 на обычных строках. Таким образом,
в худшем случае поиск становится линейным по длине группы, а вставка серии таких ключей — квадратичной.

Подробные таблицы и команды запуска приведены в benchmarks.md. Локально прошли 46 тестов JUnit 5.
