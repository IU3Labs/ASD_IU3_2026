# Отчёт по ЛР2 — задачи 1A, 1B, 1C, 1D

## Идея решения

Очередь с приоритетом представлена полным двоичным деревом внутри собственного Object[].
В каждой паре родитель/ребёнок родитель имеет не больший приоритет по компаратору.
Для естественного порядка это min-heap; обратный компаратор превращает её в max-heap.
Готовые коллекции в реализации структуры не используются.

При вставке элемент помещается в конец и поднимается до подходящего места.
При извлечении корня на его место переносится последний элемент и опускается вниз.
При удалении по значению сначала находится первое равное значение; перенесённый последний
элемент просеивается вверх или вниз в зависимости от его отношения к родителю.
Построение из массива начинается с последних внутренних узлов, поэтому даёт O(n).

## Ручные примеры

| Вход/действие | Ожидаемый результат | Что проверяет |
|---|---|---|
| Пустая очередь: poll и peek | NoSuchElementException | Ошибки на пустой структуре |
| add: 5, −2, 0, 7; затем poll до конца | −2, 0, 5, 7 | Естественный порядок и отрицательные числа |
| Те же числа, reverseOrder | 7, 5, 0, −2 | Max-heap через компаратор |
| [1, 2, 3, 4, 5, 6, 7], remove(2) | 1, 3, 4, 5, 6, 7 при извлечении | Просеивание замены вниз |
| [1, 10, 2, 11, 12, 3, 4], remove(11) | 1, 2, 3, 4, 10, 12 при извлечении | Просеивание замены вверх |
| [2, 2, 2], remove(2) | Два элемента 2 | Удаляется одно вхождение |
| [1, 2], remove(9) | false, размер 2 | Отсутствующий элемент не меняет очередь |
| Изменить исходный массив после конструктора | Очередь не изменится | Независимая копия массива |

## Сложность

`add` — O(log n) амортизированно (отдельное расширение O(n)), `poll` — O(log n),
`peek`, `size`, `isEmpty` — O(1), `remove` — O(n), heapify — O(n).
Память — O(C) для ёмкости массива, при росте O(n); после удаления ёмкость не уменьшается.
Подробное обоснование находится в `complexity.md`.

## Проверка

Тесты покрывают граничные случаи, рост массива, обе стороны восстановления кучи,
сравнение по компаратору и удаление по equals, а также min/max-режимы.
Дифференциальные проверки сравнивают случайные операции со стандартной PriorityQueue.
Счётчик сравнений проверяет линейность heapify на 100 000 элементах.
Команда `mvn -pl 32-KhusainovTI -am clean verify` включает порог покрытия строк 80%.

Результат выполненной проверки: **30 тестов, 0 ошибок, 0 провалов, 0 пропусков**.
JaCoCo: строки 82/83 (**98,80%**), ветви 35/36 (**97,22%**), методы 16/16 (**100%**).

Бенчмарки используют 10 000, 50 000 и 100 000 элементов, прогрев JVM и повторные замеры.
Реальные результаты, методика и ограничения приведены в `benchmarks.md`.
Они характеризуют конкретную среду запуска; отдельный измеритель потребления памяти не используется.

В выполненном запуске на 100 000 случайных чисел собственная min-heap затратила 22,564 мс
на заполнение и опустошение, max-heap — 23,295 мс; разница около 3,2% не меняет их асимптотику.
Построение собственной кучи из случайного массива через heapify заняло 2,248 мс против 4,051 мс
при последовательных вставках; для убывающего массива — 1,658 мс против 4,767 мс.
Полные таблицы включают сравнение с `java.util.PriorityQueue`.
