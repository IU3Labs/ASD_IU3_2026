# Лабораторная № 2 — очередь с приоритетом

Выполнены **1A, 1B, 1C, 1D: 8 баллов**, при требовании не менее 7.
Остальные задачи из пула ЛР2 не входят в выбранный набор. ЛР1 не изменялась.

| Задача | Реализация |
|---|---|
| 1A, 2 балла | Собственная двоичная min-heap на расширяемом массиве, отдельные siftUp/siftDown |
| 1B, 2 балла | Comparator, естественный порядок по умолчанию, min/max-режимы и сравнение на 100 000 чисел |
| 1C, 2 балла | Удаление первого равного элемента, восстановление в нужном направлении |
| 1D, 2 балла | Конструктор из массива с bottom-up heapify за O(n), сравнение со вставками |

## Сборка и проверка

Нужны **JDK 21+ и Maven 3.9+**. Из корня репозитория:

```sh
mvn -pl 32-KhusainovTI -am clean verify
```

Либо из папки модуля:

```sh
mvn clean verify
```

`verify` запускает JUnit 5, формирует отчёт JaCoCo в `target/site/jacoco/index.html`
и проверяет покрытие строк не менее 80%. Собственный код не зависит от сторонних библиотек.
JUnit и стандартная очередь используются в тестовой части.

Исходный пример курса рассчитан на Java 25. Новый модуль явно использует Java 21 и JUnit 5,
как разрешено `docs/style-guide.md` и условием ЛР2. Команда с `-pl` собирает выбранный модуль
и родительский POM; исходный `00-example-module` не требуется изменять.
Для сборки **всех** исходных модулей репозитория потребуется Java 25 и зависимости исходного примера.

## Использование

```java
PriorityQueueCustom<Integer> min = new PriorityQueueCustom<>();
min.add(5);
min.add(1);
min.add(3);
System.out.println(min.poll()); // 1
System.out.println(min.peek()); // 3, размер не меняется
min.remove(5);                 // true

PriorityQueueCustom<Integer> max =
        new PriorityQueueCustom<>(Comparator.reverseOrder());
max.add(1);
max.add(5);
System.out.println(max.poll()); // 5

PriorityQueueCustom<Integer> built =
        new PriorityQueueCustom<>(new Integer[]{9, 2, 4}); // O(n)
```

Импорты: `ru.bmstu.lab02.PriorityQueueCustom`, `java.util.Comparator`.
В естественном порядке элементы должны реализовывать `Comparable`; с компаратором это не требуется.
Конструктор из массива копирует его, не меняет исходный порядок и не сохраняет ссылку на исходный массив.

`null` при добавлении, в массиве или вместо массива запрещён (`NullPointerException`).
`null` вместо компаратора включает естественный порядок. `poll()` и `peek()` на пустой очереди
бросают `NoSuchElementException` — поведение `peek` выбрано явно, поскольку условие его не уточняет.
`remove(null)` и удаление отсутствующего значения возвращают `false`.
Равенство для `remove` определяется через `equals`, а приоритет — через компаратор;
это разные проверки. Первым вхождением считается первое совпадение при обходе внутреннего массива.
Порядок извлечения элементов с равным приоритетом не гарантируется.

## Тесты и эксперименты

30 JUnit-тестов: пустая очередь, один элемент, отрицательные числа, дубликаты, экстремальные `int`,
расширение на 100 000 элементах, копирование массива, запрет `null`, min/max, объекты без `Comparable`,
удаление корня/середины/последнего элемента, восстановление вверх и вниз, равенство и приоритет.
Дифференциальный тест выполняет по 20 000 случайных операций для min и max
и после каждой сравнивает результат, размер и вершину со стандартной очередью.
Для убывающего массива из 100 000 элементов проверяется линейное число сравнений при heapify.

Повторение замеров из корня репозитория, после сборки:

```sh
java -Xms256m -Xmx256m -cp 32-KhusainovTI/target/test-classes:32-KhusainovTI/target/classes ru.bmstu.lab02.HeapBenchmark
```

В **Windows PowerShell** разделитель classpath — точка с запятой; всю строку пути нужно взять в кавычки:

```powershell
java -Xms256m -Xmx256m -cp "32-KhusainovTI/target/test-classes;32-KhusainovTI/target/classes" ru.bmstu.lab02.HeapBenchmark
```

Чтобы сохранить новые результаты, добавьте `> benchmarks-new.md` к команде запуска.

[benchmarks.md](benchmarks.md), расчёт сложности — в [complexity.md](complexity.md),
краткий отчёт — в [report.md](report.md).
