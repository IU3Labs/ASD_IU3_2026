# Расчёт асимптотики ЛР №2

`n` — число элементов, `C` — текущая ёмкость массива или таблицы. Сравнение элементов, `equals` и `hashCode` считаются операциями `O(1)`.

## Очередь с приоритетом (1A, 1C, 1D)

| Операция | Время | Обоснование |
|---|---|---|
| `add` | Амортизированно `O(log n)`. Вызов с расширением занимает `O(n)`. | Просеивание вверх проходит не больше высоты кучи. При удвоениях суммарный объём копирования за серию вставок линейный. |
| `poll` | `O(log n)` | Последний элемент переносится в корень. Просеивание вниз проходит не больше высоты кучи. |
| `peek`, `size`, `isEmpty` | `O(1)` | Чтение корня или счётчика размера. |
| `remove` | `O(n)` | Поиск первого совпадения по массиву занимает до `n` сравнений. Перенос последнего элемента и просеивание в одном направлении добавляют `O(log n)`. |
| `PriorityQueueCustom(T[] array)` | `O(n)` | Проверка и копирование занимают `O(n)`. Просеивание идёт от последнего внутреннего узла к корню. |

Узлов, которые могут опуститься хотя бы на `h` уровней, не больше `n / 2^h`. Поэтому суммарное число шагов просеивания ограничено суммой `n/2 + n/4 + n/8 + …`, которая не превосходит `n`. Конструктор выделяет `O(n)` памяти для копии массива. Построение последовательными `add` в худшем случае занимает `O(n log n)` времени, например при вставке различных элементов в порядке убывания.

Массив занимает `O(C)` памяти. Просеивание выполняется циклом с `O(1)` дополнительной памяти. Во время расширения копия массива временно занимает ещё `O(C)` памяти. После удаления элементов массив не уменьшается, поэтому очередь может занимать больше памяти, чем требуется для текущего числа элементов.

## Хеш-таблица с линейным пробированием (2A)

| Операция | При равномерном распределении хешей | Худший случай |
|---|---|---|
| `get`, `containsKey`, `remove` | В среднем `O(1)` | `O(C)` |
| `put` | Амортизированно в среднем `O(1)` | `O(C)` без перехеширования, `O(C + n²)` с перехешированием при массовых коллизиях |
| `size`, `capacity` | `O(1)` | `O(1)` |

Поиск начинает пробирование с `abs((long) key.hashCode()) % C`. Приведение к `long` сохраняет корректность для `Integer.MIN_VALUE`. При коллизии проверяется следующая ячейка, а `DELETED` пропускается. Доля живых записей ограничена 75%, а доля занятых ячеек с учётом `DELETED` — 87,5%. Поэтому поиск останавливается на ключе или на пустой ячейке после максимум `C` проверок. При равномерных хешах среднее число проверок ограничено константой.

При перехешировании просматривается старый массив и заново размещаются `n` записей. При равномерных хешах это занимает `O(C + n)`, то есть `O(C)`. Удвоения ёмкости дают линейный суммарный объём работы на серии вставок. После очистки `DELETED` при той же ёмкости нужно занять как минимум `C/8` дополнительных ячеек, прежде чем очистка сможет повториться. Если все `n` ключей начинают пробирование с одного индекса, их повторное размещение требует до `1 + 2 + … + n` проверок. Это даёт худшую оценку `O(C + n²)`.

Два массива занимают `O(C)` памяти. Маркер `DELETED` общий для всех удалённых ячеек, а ссылка на удалённое значение очищается. При перехешировании старые и новые массивы временно существуют одновременно, что даёт `O(C)` дополнительной памяти. Поиск, обновление и удаление без перехеширования используют `O(1)` дополнительной памяти.
