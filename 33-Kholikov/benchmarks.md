# Бенчмарки ЛР №2

Замеры выполнены 15 ноября 2026 года на AMD Ryzen 9 5900HX, Windows x64 (сборка 26300), Java HotSpot 26.0.2.1. Параметры JVM в каждом запуске одинаковы: `-Xms512m -Xmx512m -XX:+UseG1GC`.

## Методика

- Для каждого размера использован набор уникальных случайных `Integer` с начальным значением генератора 42. Для перемешивания порядка поиска и удаления использовано значение 43. Наборы данных у сравниваемых реализаций одинаковые.
- Запустили три отдельных процесса JVM последовательно. В каждом было пять раундов прогрева и девять измерений для каждого сочетания структуры, операции и размера. Порядок сценариев разворачивался в каждом втором раунде.
- В таблицах приведено среднее арифметическое **27 измерений**. Время всего пакета операций измерялось через `System.nanoTime()`. Генерация данных и заполнение перед `get` и `remove` происходили до запуска таймера. Сценарии `add` + `poll` и `put` начинались с создания пустой структуры, включая расширения при заполнении.
- Для 1C измеряли 256 последовательных успешных удалений по значению из очереди начального размера N. Для таблицы измеряли N вставок, N успешных поисков и N удалений. В каждом сценарии проверялась контрольная сумма или число обработанных элементов.

## Построение кучи из массива (1D)

На одном и том же массиве из 100 000 элементов измерили только построение `PriorityQueueCustom`. Время последовательных `add` включает рост массива, а время конструктора включает проверку и копирование исходных данных.

| Способ | N элементов | Среднее время (мс) | Выделено на одно построение (КиБ) |
|---|---:|---:|---:|
| Последовательные `add` | 100 000 | 2,687 | 1024,2 |
| Просеивание снизу вверх | 100 000 | 1,944 | 390,7 |

На этом наборе построение снизу вверх в среднем заняло на 28% меньше времени. Оно выделило один массив нужной ёмкости, тогда как последовательные вставки несколько раз расширяли массив.

## Как повторить

Из корня репозитория в PowerShell с JDK 25 или новее.

```powershell
mvn -pl 33-Kholikov test-compile
$classpath = '33-Kholikov/target/classes;33-Kholikov/target/test-classes'
$output = '33-Kholikov/target/lab02-benchmark'
New-Item -ItemType Directory -Path $output -Force | Out-Null
foreach ($run in 1..3) {
    java -Xms512m -Xmx512m -XX:+UseG1GC -cp $classpath ru.bmstu.lab2.Lab02Benchmark |
        Set-Content -Encoding utf8 "$output/run-$run.csv"
}
```

Результаты из трёх CSV группируются по `structure`, `operation` и `size`. Для каждой группы вычисляется среднее `elapsed_ns` и делится на 1 000 000, чтобы получить миллисекунды. Среднее `allocated_bytes` делится на 1 024 для перевода в КиБ.

## Выводы

При 100 000 элементов стандартная очередь быстрее выполнила `add` + `poll` и удаление по значению, а собственная хеш-таблица быстрее выполнила `put`, `get` и `remove`. Поиск элемента перед удалением из очереди в обеих реализациях занимает `O(n)`, поэтому эта операция заметно замедляется с ростом размера очереди. За цикл `add` + `poll` собственная очередь выделила около 1 024 КиБ, стандартная — 1 757 КиБ из-за разных правил расширения массива. При заполнении собственная таблица выделила около 4 096 КиБ, стандартная — 5 173 КиБ, поскольку собственная реализация хранит записи в двух массивах без отдельных объектов для каждой записи.
