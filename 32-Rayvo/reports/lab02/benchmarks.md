# Бенчмарки lab02 — группа 1

Общий Integer[]: Random(20261118), значения во всём диапазоне int.
Сценарии чередуются с циклическим сдвигом порядка. Замер — System.nanoTime().
Создание набора и упаковка Integer исключены; создание очереди и расширения включены.
add + poll: сначала N вставок, затем N извлечений до пустой очереди.
build: только построение, без извлечений; копирование массива и выделение памяти включены.
Результаты используются через volatile, чтобы вычисления не были устранены JIT.
Повторный запуск из 32-Rayvo: `mvn test-compile exec:java`.

## Задача 1B — min-heap и max-heap на одном наборе 100 000 элементов

| Вариант | Среднее время add + poll (мс) | Медиана (мс) | Отклонение (мс) |
|---|---:|---:|---:|
| 1B min | 25.308 | 24.152 | 1.611 |
| 1B max | 24.650 | 24.626 | 0.826 |

Оба режима имеют O(n log n): меняется направление сравнения, а не высота дерева.
Различия замеров объясняются сравнением, разными путями просеивания, JIT и шумом среды;
по одному набору нельзя утверждать, что min-heap или max-heap всегда быстрее.

## Задача 1D — последовательные add и линейное построение

| Построение | N элементов | Среднее время (мс) | Медиана (мс) | Сложность в худшем случае |
|---|---:|---:|---:|---|
| 1D add | 10000 | 0.209 | 0.171 | O(n log n) |
| 1D heapify | 10000 | 0.149 | 0.136 | O(n) |
| JDK heapify | 10000 | 0.790 | 0.189 | O(n) |
| 1D add | 50000 | 1.011 | 0.798 | O(n log n) |
| 1D heapify | 50000 | 0.677 | 0.679 | O(n) |
| JDK heapify | 50000 | 0.503 | 0.443 | O(n) |
| 1D add | 100000 | 1.764 | 1.727 | O(n log n) |
| 1D heapify | 100000 | 1.753 | 1.651 | O(n) |
| JDK heapify | 100000 | 1.109 | 1.029 | O(n) |

На 100 000 элементах: последовательные add — 1.764 мс, heapify — 1.753 мс.
Отношение времени add / heapify — 1.01; это результат одного запуска.
Heapify обрабатывает внутренние узлы снизу вверх, без повторных вставок и расширений.
Случайный набор часто даёт линейное ожидаемое суммарное время add; разрыв с heapify
на нём может быть небольшим. Худшая граница последовательных add остаётся O(n log n).

## Выводы о скорости и памяти

На 100 000 элементах в add + poll быстрее java.util.PriorityQueue; при одинаковой асимптотике
разница связана с присваиваниями, сравнением и оптимизациями JVM.
Оба режима используют O(n) памяти для пикового числа элементов n, а компаратор добавляет O(1).
Конструктор массива выделяет max(16, n) ссылок; последовательные add оставляют запас
ёмкости при удвоении и временно удерживают старый массив во время копирования.
Точные байты памяти здесь не измерялись: они зависят от размера ссылок и настроек JVM.
