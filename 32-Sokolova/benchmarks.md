# Лабораторная работа №2. Бенчмарки

## 1. Условия эксперимента

Измерения выполнены на компьютере под управлением macOS с использованием Java 21.

Для измерения времени применялся метод `System.nanoTime()`. Каждый эксперимент повторялся 5 раз, после чего вычислялось среднее время выполнения.

Перед основными измерениями выполнялся прогрев JVM.

## 2. Сравнение очередей с приоритетом

Измерялись последовательное добавление всех элементов и последующее извлечение всех элементов.

| Структура | Операция | N | Среднее время, мс |
|---|---|---:|---:|
| PriorityQueueCustom | add + poll | 10 000 | 4,620 |
| java.util.PriorityQueue | add + poll | 10 000 | 4,476 |
| PriorityQueueCustom | add + poll | 50 000 | 20,885 |
| java.util.PriorityQueue | add + poll | 50 000 | 16,874 |
| PriorityQueueCustom | add + poll | 100 000 | 45,818 |
| java.util.PriorityQueue | add + poll | 100 000 | 34,484 |

## 3. Сравнение хеш-таблиц

Измерялись вставка N пар «ключ — значение» и последующий поиск всех N ключей.

| Структура | Операция | N | Среднее время, мс |
|---|---|---:|---:|
| HashMapCustom | put + get | 10 000 | 3,412 |
| java.util.HashMap | put + get | 10 000 | 3,834 |
| HashMapCustom | put + get | 50 000 | 10,966 |
| java.util.HashMap | put + get | 50 000 | 8,306 |
| HashMapCustom | put + get | 100 000 | 20,342 |
| java.util.HashMap | put + get | 100 000 | 30,769 |

## 4. Сравнение алгоритма Top-K с полной сортировкой

Размер входного списка: 1 000 000 элементов.

Количество выбираемых наибольших элементов: k = 100.

| Алгоритм | Среднее время, мс |
|---|---:|
| Собственный Top-K | 24,843 |
| Полная сортировка Java | 441,554 |

Алгоритм Top-K оказался приблизительно в 17,8 раза быстрее полной сортировки на выбранных данных.

## 5. Выводы

С увеличением числа элементов время выполнения операций возрастает, что соответствует ожидаемому поведению исследуемых структур данных.

Стандартная очередь `java.util.PriorityQueue` показала меньшее время выполнения, чем собственная реализация. Результаты сравнения хеш-таблиц оказались неоднозначными: преимущество зависело от размера набора данных.

Наибольшая разница наблюдалась при сравнении алгоритма Top-K с полной сортировкой. Использование min-кучи ограниченного размера позволяет не сортировать все элементы, существенно сокращая время обработки при небольшом k.

Различия между реализациями могут объясняться особенностями внутренней организации структур, оптимизацией JVM, выделением памяти и работой сборщика мусора. Измерения не включали отдельное профилирование потребления памяти.
