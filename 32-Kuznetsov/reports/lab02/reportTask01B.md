## Условие

Очередь с приоритетом, конструктор которой принимает `Comparator<T>` (без него — естественный порядок).
Класс должен работать и как min-heap, и как max-heap. Сравнить время min- и max-варианта на одном наборе
из 100 000 случайных элементов и объяснить результат.

## 1. Идея решения и структура данных

Структура данных та же, что в задаче 1A, — двоичная куча на массиве. Чтобы не копировать код кучи,
`ComparatorPriorityQueue<T>` **наследуется** от `PriorityQueueCustom<T>` и переопределяет только один
метод — `compare`:

```java
@Override
protected int compare(T first, T second) {
    if (order == null) {
        return super.compare(first, second);
    }
    return order.compare(first, second);
}
```

`siftUp` и `siftDown` в базовом классе вызывают `compare`, поэтому они автоматически начинают работать по новому
порядку. Куча всегда держит в корне элемент, «наименьший по компаратору»:

- обычный компаратор → в корне минимум → **min-heap**;
- обратный компаратор (`Comparator.reverseOrder()`) → «наименьший» по нему — это максимум → **max-heap**.

Для удобства добавлены две фабрики: `ComparatorPriorityQueue.minHeap()` и `ComparatorPriorityQueue.maxHeap()`.
Конструктор без параметров передаёт `null`, и тогда используется естественный порядок из базового класса.
Тип компаратора `Comparator<? super T>`: так подходит, например, компаратор для `Number` к очереди `Integer`.

## 2. Анализ асимптотики

| Операция | Время | Доп. память |
|---|---|---|
| конструктор, `minHeap()`, `maxHeap()` | O(1) | O(1) |
| `compare` | O(1) + время самого компаратора | O(1) |
| `add` | O(log n) амортизированно | O(1), при расширении O(n) |
| `poll` | O(log n) | O(1) |
| `peek`, `size`, `isEmpty` | O(1) | O(1) |

### Обоснование кодом

В классе задачи 1B нет циклов: конструкторы и фабрики только сохраняют ссылку на компаратор,
а `compare` делает одну проверку на `null` и один вызов. Значит, все операции добавляют к базовой
куче только O(1) на каждое сравнение:

```java
public ComparatorPriorityQueue(Comparator<? super T> order) {
    super();
    this.order = order;
}
```

`add` и `poll` полностью берутся из задачи 1A, где каждое просеивание проходит путь длиной не больше
`⌊log₂ n⌋` (расчёт — в `reportTask01A.md`). Число сравнений не зависит от того, min это куча или max, поэтому
асимптотика у обоих режимов одинаковая: O(log n) на операцию и O(n log n) на `n` вставок + `n` извлечений.

Дополнительная память — одно поле `order`, то есть O(1) сверх памяти кучи (O(n)).

## 3. Сравнение min и max на 100 000 элементах

Запуск — `Lab02Benchmark.main`, один и тот же массив из 100 000 случайных чисел (`new Random(25)`),
цикл «100 000 `add` + 100 000 `poll`», 5 прогревочных прогонов + 20 замеряемых.

| Вариант | Среднее время (мс) | Число сравнений |
|---|---|---|
| min-heap (без компаратора, `null`) | 40.306 | 3 060 679 |
| min-heap (`Comparator.naturalOrder()`) | 40.123 | 3 060 679 |
| max-heap (`Comparator.reverseOrder()`) | 42.585 | 3 058 989 |

**Объяснение.** Время почти одинаковое (разница около 5 %), и это ожидаемо:

1. Алгоритм один и тот же, отличается только результат `compare`. Число сравнений у min и max почти
   совпадает: ≈3.06 млн ≈ 1.84 · n · log₂n. Небольшое отличие — из-за того, что для max-кучи те же данные лежат
   в другом порядке относительно компаратора.
2. Случайные данные симметричны: для min-кучи и для max-кучи они «одинаково случайные», поэтому
   в среднем элементы поднимаются и опускаются на одинаковую глубину.
3. Оставшаяся разница — это стоимость вызова компаратора и работа JIT-компилятора. `Comparator.reverseOrder()`
   внутри вызывает `b.compareTo(a)`, то есть это лишний уровень вызова. Кроме того, метод `compare` сначала
   компилируется под один компаратор и потом перекомпилируется под другой. При повторных запусках разница
   между вариантами меняется в пределах шума, а иногда быстрее оказывается max-куча.

Вывод: max-heap через компаратор не медленнее min-heap по асимптотике и практически не медленнее по времени.

## 4. Ручные тесты

11 тестов.

| Тест | Что проверяет | Граничный случай |
|---|---|---|
| `shouldUseNaturalOrderWithoutComparator` | конструктор без параметров = естественный порядок | компаратор `null` |
| `shouldWorkAsMinHeap` | `minHeap()`, есть отрицательные числа | — |
| `shouldWorkAsMaxHeap` | `maxHeap()`, `peek` возвращает максимум | — |
| `shouldPollMaxHeapInNonIncreasingOrder` | 1000 случайных чисел, порядок невозрастания | большой набор |
| `shouldGiveMirroredOrderForMinAndMax` | на одних данных min и max дают обратный порядок | оба режима сразу |
| `shouldUseCustomComparatorForStrings` | строки по длине | свой компаратор |
| `shouldUseCustomComparatorByAbsoluteValue` | числа по модулю | порядок не совпадает с обычным |
| `shouldKeepDuplicatesInMaxHeap` | дубликаты в max-куче | дубликаты |
| `shouldThrowWhenMaxHeapIsEmpty` | `poll` и `peek` на пустой max-куче | пустая очередь |
| `shouldWorkWithSingleElementInMaxHeap` | один элемент | один элемент |
| `shouldThrowWhenAddingNullWithComparator` | `add(null)` запрещён | null |

**Почему эти тесты важны.** Главное в задаче — оба режима, поэтому есть тесты и на min, и на max, и тест,
где они сравниваются друг с другом на одних данных. Компараторы «по длине» и «по модулю» показывают, что
куча действительно использует переданный компаратор, а не `compareTo`.
