## Условие

Реализовать `HashMapCustom<K, V>` с линейным пробированием: `put`, `get` (значение или `null`), `containsKey`,
`remove`, `size`, `capacity`. Хеш-функция `Math.abs(key.hashCode()) % capacity`. Коэффициент загрузки
не больше 0.75, при превышении ёмкость увеличивается в 2 раза с перехешированием. Для удалённых ячеек нужен
маркер `DELETED`.

## 1. Идея решения и структура данных

Структура данных — **хеш-таблица с открытой адресацией**. Пары хранятся не в списках, а прямо в двух массивах
одинаковой длины: `keySlots` (ключи) и `valueSlots` (значения). Ключ и его значение лежат под одним индексом.
Такой вариант проще варианта с отдельным классом `Entry` и не создаёт объект на каждую пару.

- **Индекс ключа:** `Math.abs(key.hashCode()) % capacity`.
- **Коллизия:** если ячейка занята другим ключом, проверяется следующая — `(index + 1) % capacity`, по кругу.
- **Поиск** (`locate`) идёт по цепочке до пустой ячейки `null`: если дошли до `null`, ключа нет.
- **Удаление:** ячейка помечается объектом-маркером `DELETED`. Если записать туда `null`, поиск остановился бы
  на этой дыре и не нашёл ключи, которые при вставке прошли дальше по цепочке.
- **Вставка** (`put`): сначала `locate` ищет ключ — если он есть, обновляется значение. Если нет,
  `freeSlot` находит первую ячейку `null` **или** `DELETED`, так удалённые ячейки используются повторно.
  Поиск идёт первым, поэтому ключ не может попасть в таблицу дважды.

### Как считается загрузка

Кроме `size` (живые ключи) хранится `usedSlots` — сколько ячеек не `null`, то есть ключи вместе с `DELETED`.
Маркеры тоже удлиняют цепочки поиска, поэтому загрузка считается по `usedSlots`:

```java
if (usedSlots > keySlots.length * MAX_LOAD) {
    rebuild();
}
```

При перестройке (`rebuild`) все `DELETED` выбрасываются. Новая ёмкость:

```java
int tombstones = usedSlots - size;
int newCapacity = tombstones > size ? keySlots.length : keySlots.length * 2;
```

- обычно ёмкость удваивается (как требует условие);
- если удалённых ячеек больше, чем живых ключей, таблица перестраивается с той же ёмкостью.
  Без этого при чередовании `put`/`remove` ёмкость росла бы бесконечно, хотя ключей почти нет.

После каждой вставки занято не больше 75 % ячеек, поэтому в таблице всегда есть ячейка `null`,
и циклы `while` в `locate` и `freeSlot` всегда заканчиваются.

### Граничные случаи

- `Math.abs(Integer.MIN_VALUE)` в Java равен `Integer.MIN_VALUE`, то есть отрицательный. У ключа
  `Integer.MIN_VALUE` именно такой `hashCode`, и формула даёт отрицательный индекс. Поэтому в `indexFor`
  отрицательный остаток переворачивается: `return index < 0 ? -index : index;`.
- Ключ `null` запрещён во всех методах (`IllegalArgumentException`), значение `null` разрешено.
- Ёмкость в конструкторе должна быть не меньше 1.

## 2. Анализ асимптотики

`n` — число ключей, `m` — ёмкость, `α = usedSlots / m ≤ 0.75`.

| Операция | Среднее время | Худшее время | Доп. память |
|---|---|---|---|
| `put` | O(1) амортизированно | O(n) | O(1), при `rebuild` O(m) |
| `get` | O(1) | O(n) | O(1) |
| `containsKey` | O(1) | O(n) | O(1) |
| `remove` | O(1) | O(n) | O(1) |
| `size`, `capacity` | O(1) | O(1) | O(1) |
| Вся структура | — | — | O(m), без удалений `m < 2.67 · n` |

### Обоснование кодом

**`locate` / `freeSlot` — O(1) в среднем.** Оба метода — один цикл по цепочке занятых ячеек:

```java
int index = indexFor(key);
while (keySlots[index] != null) {
    if (keySlots[index] != DELETED && keySlots[index].equals(key)) {
        return index;
    }
    index = next(index);
}
return -1;
```

Длина цепочки зависит от загрузки, а не от `n`. Для линейного пробирования среднее число проверок (оценка Кнута):
при успешном поиске `½ · (1 + 1/(1 − α))`, при неуспешном `½ · (1 + 1/(1 − α)²)`.
При максимальной загрузке `α = 0.75` это **2.5** и **8.5** проверки — константы, поэтому в среднем O(1).
В худшем случае все ключи попадают в один индекс и стоят одной цепочкой — тогда цикл проходит O(n) ячеек.

**`get`, `containsKey`, `remove`** — это `requireKey` (O(1)) + один `locate` + O(1) действий, итого O(1) в среднем.

**`put` — O(1) амортизированно.** `locate` + `freeSlot` + запись — O(1) в среднем. `rebuild()` проходит по старому
массиву и вставляет `size` ключей, то есть O(m) = O(n), но вызывается редко:

- при удвоении ёмкости суммарная работа на все перестройки при `n` вставках меньше `m + m/2 + m/4 + … < 2m`, то есть O(1) на вставку;
- перестройка с той же ёмкостью бывает, только когда маркеров больше половины занятых ячеек. После неё занято меньше
  `0.375 · m`, значит до следующей нужно не меньше `0.375 · m` новых вставок — тоже O(1) на вставку в среднем.

**Дополнительная память.** Все методы, кроме `rebuild`, используют несколько локальных переменных — O(1).
`rebuild` на время перестройки держит старые и новые массивы — O(m). Сама таблица — два массива по `m` ссылок.
Без удалений `n / 0.75 ≤ m < 2n / 0.75`, то есть память O(n).

## 3. Ручные тесты

19 тестов.

| Тест | Что проверяет | Граничный случай |
|---|---|---|
| `shouldBeEmptyWhenCreated` | пустая таблица, ёмкость 16, `get` → `null` | пустая таблица |
| `shouldPutAndGetValue` | базовые `put`/`get` | — |
| `shouldUpdateValueForExistingKey` | повторный `put` обновляет значение, `size` не растёт | существующий ключ |
| `shouldContainOnlyAddedKeys` | `containsKey` для есть/нет | отсутствующий ключ |
| `shouldStoreNullValue` | значение `null` хранится и отличается от «нет ключа» | null-значение |
| `shouldRemoveExistingKey` | `remove` удаляет только нужный ключ | — |
| `shouldReturnFalseWhenRemovingMissingKey` | повторное удаление → `false` | отсутствующий ключ |
| `shouldReturnFalseWhenRemovingFromEmptyMap` | удаление из пустой таблицы | пустая таблица |
| `shouldThrowWhenKeyIsNull` | ключ `null` во всех 4 методах | null-ключ |
| `shouldThrowWhenCapacityIsNotPositive` | ёмкость 0 и −25 | неверный аргумент |
| `shouldGrowFromCapacityOne` | таблица ёмкости 1 сама растёт | минимальная ёмкость |
| `shouldDoubleCapacityWhenLoadFactorIsExceeded` | 12 ключей → ёмкость 16, 13-й → 32 (13/16 = 0.81 > 0.75) | ровно на пороге 0.75 |
| `shouldKeepAllElementsAfterResize` | 10 000 ключей после многих перестроек | много ресайзов |
| `shouldFindKeyBehindDeletedSlot` | ключи `5, 15, 25` при ёмкости 10 в одной цепочке, удаляем `15`, `25` находится | **маркер `DELETED`** |
| `shouldNotDuplicateKeyWhenDeletedSlotIsBeforeIt` | `put(25)` после удаления `15` не создаёт копию | повторное использование `DELETED` |
| `shouldWrapAroundEndOfTable` | ключ `19` при ёмкости 10 переходит из ячейки 9 в ячейку 0 | конец массива |
| `shouldWorkWithNegativeHashCodes` | ключи `-25` и `Integer.MIN_VALUE` | отрицательный `hashCode` |
| `shouldNotGrowWhenKeysAreAddedAndRemovedManyTimes` | 1000 раз `put`+`remove`, ёмкость остаётся 16 | перестройка с той же ёмкостью |
| `shouldMatchJavaHashMapOnRandomOperations` | 20 000 случайных операций, сверка с `java.util.HashMap` | большой набор |

**Почему эти тесты важны.** Ключи `5, 15, 25` при ёмкости 10 специально дают одинаковый индекс 5, чтобы проверить
цепочку пробирования и маркер `DELETED`. Если заменить `DELETED` на `null` (остановку поиска), падают 4 теста.
Тест с `Integer.MIN_VALUE` падает с `ArrayIndexOutOfBoundsException`, если убрать проверку отрицательного индекса.
Случайный тест сравнивает каждый ответ со стандартной `HashMap`.
