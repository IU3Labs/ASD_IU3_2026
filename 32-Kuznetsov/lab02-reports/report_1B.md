# Отчёт по задаче 1B. Min-heap и max-heap через компаратор

**Студент:** Кузнецов Д.А., группа ИУ3-32Б, вариант 25
**Код:** `src/main/java/ru/bmstu/lab02/task1b/OrderedPriorityQueue.java`
**Тесты:** `src/test/java/ru/bmstu/lab02/task1b/OrderedPriorityQueueTest.java`

## Условие

Очередь с приоритетом, конструктор которой принимает `Comparator<T>` (без него — естественный порядок).
Класс должен работать и как min-heap, и как max-heap. Сравнить время min- и max-варианта на одном наборе
из 100 000 случайных элементов и объяснить результат.

## 1. Идея решения и структура данных

Структура данных та же, что в задаче 1A, — двоичная куча на массиве. В задаче 1A порядок уже хранится
в поле-компараторе `order`, и все сравнения в `siftUp`/`siftDown` идут через него. Поэтому классу
`OrderedPriorityQueue<T>` не нужно ничего переопределять — он только **передаёт компаратор в конструктор базового класса**:

```java
public OrderedPriorityQueue(Comparator<? super T> order) {
    super(order);
}
```

В базовом классе `null` заменяется естественным порядком:

```java
this.order = order != null ? order : naturalOrder();
```

Куча всегда держит в корне элемент, «наименьший по компаратору»:

- обычный порядок → в корне минимум → **min-heap**;
- `Comparator.reverseOrder()` → «наименьший» по нему — это максимум → **max-heap**.

Для удобства есть фабрики `OrderedPriorityQueue.minHeap()` и `OrderedPriorityQueue.maxHeap()`.
Тип компаратора `Comparator<? super T>`: подходит, например, компаратор для `Number` к очереди `Integer`.

Почему так, а не отдельный класс для max-кучи: направление приоритета — это только способ сравнения,
алгоритм кучи от него не зависит. Один класс с компаратором покрывает оба режима и любой другой порядок.

## 2. Анализ асимптотики

| Операция | Время | Доп. память |
|---|---|---|
| конструкторы, `minHeap()`, `maxHeap()` | O(1) | O(1) |
| одно сравнение | O(1) + время самого компаратора | O(1) |
| `add` | O(log n) амортизированно | O(1), при расширении O(n) |
| `poll` | O(log n) | O(1) |
| `peek`, `size`, `isEmpty` | O(1) | O(1) |

### Обоснование кодом

В классе задачи 1B нет циклов: конструкторы и фабрики только передают компаратор в базовый класс —
это O(1). Сравнение в базовом классе — один вызов компаратора:

```java
private int compare(Object first, Object second) {
    return order.compare((T) first, (T) second);
}
```

`add` и `poll` полностью берутся из задачи 1A, где каждое просеивание проходит путь длиной не больше
`⌊log₂ n⌋` (расчёт — в `report_1A.md`). Число сравнений не зависит от того, min это куча или max, поэтому
асимптотика у обоих режимов одинаковая: O(log n) на операцию и O(n log n) на `n` вставок + `n` извлечений.

Дополнительная память — одна ссылка на компаратор, O(1) сверх памяти кучи (O(n)).

## 3. Сравнение min и max на 100 000 элементах

Запуск — `BenchmarkRunner.main`, один и тот же массив из 100 000 случайных чисел (`new Random(25)`),
цикл «100 000 `add` + 100 000 `poll`», 5 прогревочных прогонов + 20 замеряемых.

| Вариант | Среднее время (мс) | Число сравнений |
|---|---|---|
| min-heap (конструктор без компаратора) | 14.059 | 3 060 679 |
| min-heap (`Comparator.naturalOrder()`) | 20.302 | 3 060 679 |
| max-heap (`Comparator.reverseOrder()`) | 34.843 | 3 058 989 |

**Объяснение.** По асимптотике и по числу сравнений варианты одинаковые, а время растёт в порядке замеров:
14 → 20 → 35 мс. Это объясняется не кучей, а тем, как JVM вызывает компаратор:

1. Алгоритм один и тот же, отличается только результат сравнения. Число сравнений почти совпадает:
   ≈3.06 млн ≈ 1.84 · n · log₂n. Небольшое отличие — из-за того, что для max-кучи те же данные лежат
   в другом порядке относительно компаратора. Куча не делает для max-варианта лишней работы.
2. Все сравнения идут через одно место в коде — `order.compare(...)` в базовом классе. В первом замере
   туда приходит только один тип компаратора, и JIT-компилятор встраивает его прямо в просеивание.
   Во втором замере типов уже два — встраивание работает хуже. В третьем (max-heap) типов три, и JVM
   переходит на обычный виртуальный вызов без встраивания на каждое из 3 млн сравнений.
3. `Comparator.reverseOrder()` внутри ещё и вызывает `b.compareTo(a)` — лишний уровень вызова.

Поэтому последний замер всегда проигрывает. На другой машине при другом порядке запуска разница
между min и max была около 5 %.

Вывод: max-heap через компаратор имеет ту же асимптотику O(n log n) и то же число сравнений, что и min-heap;
разница во времени — это стоимость вызова компаратора и оптимизации JVM, а не свойство кучи.

## 4. Ручные тесты

11 тестов.

| Тест | Что проверяет | Граничный случай |
|---|---|---|
| `shouldUseNaturalOrderWithoutComparator` | конструктор без параметров = естественный порядок | компаратор не задан |
| `shouldWorkAsMinHeap` | `minHeap()`, есть отрицательные числа | — |
| `shouldWorkAsMaxHeap` | `maxHeap()`, `peek` возвращает максимум | — |
| `shouldPollMaxHeapInNonIncreasingOrder` | 1000 случайных чисел, порядок невозрастания | большой набор |
| `shouldGiveMirroredOrderForMinAndMax` | на одних данных min и max дают обратный порядок | оба режима сразу |
| `shouldUseCustomComparatorForStrings` | строки по длине | свой компаратор |
| `shouldUseCustomComparatorByAbsoluteValue` | числа по модулю | порядок не совпадает с обычным |
| `shouldKeepDuplicatesInMaxHeap` | дубликаты в max-куче | дубликаты |
| `shouldThrowWhenMaxHeapIsEmpty` | `poll` и `peek` на пустой max-куче | пустая очередь |
| `shouldWorkWithSingleElementInMaxHeap` | один элемент | один элемент |
| `shouldThrowWhenAddingNullWithComparator` | `add(null)` запрещён | null |

**Почему эти тесты важны.** Главное в задаче — оба режима, поэтому есть тесты и на min, и на max, и тест,
где они сравниваются на одних данных. Компараторы «по длине» и «по модулю» показывают, что куча
действительно использует переданный компаратор. Если в базовом классе игнорировать компаратор, падают 7 тестов.

Ветка `order == null` в базовом классе тоже покрыта (тест `shouldUseNaturalOrderWithoutComparator`).
