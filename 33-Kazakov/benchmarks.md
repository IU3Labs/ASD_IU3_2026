# Бенчмарки лабораторной работы №2

Замеры выполнены 22 ноября 2026 года на Intel Core i3-1215U под Windows 11, Eclipse Temurin 25.0.4.1.
Для JVM задан размер кучи 512 МиБ. В каждой паре обе структуры получают одни и те же уникальные
псевдослучайные значения `Integer`, подготовленные заранее с фиксированным начальным числом.
Для каждого размера и каждой реализации выполнено 12 прогревочных и 24 измеряемых прогона.
Порядок запуска реализаций чередуется. Время измерено через `System.nanoTime()`;
в таблице приведено среднее время всего указанного набора операций.

Для очередей `add + poll` включает заполнение пустой очереди и извлечение всех элементов.
Удаление по значению измеряется отдельно: очередь заполняется заранее, затем удаляются
128 значений, равномерно выбранных из списка вставки. Для хеш-таблиц сначала вставляются `N` пар,
затем ищутся все вставленные ключи в обратном порядке, затем все эти ключи удаляются.
Каждая фаза измерена отдельно. Контрольные суммы сравниваются после замера.

Из корня репозитория в PowerShell:

```powershell
mvn -pl 33-Kazakov test-compile
java -Xms512m -Xmx512m -cp "33-Kazakov/target/classes;33-Kazakov/target/test-classes" ru.bmstu.lab2.StructureBenchmark
```

## Вывод

Стандартная очередь быстрее в цикле вставки и извлечения на всех трёх размерах, а удаление по значению
заметно дорожает у обеих очередей из-за линейного поиска. Стандартная хеш-таблица в этих замерах быстрее
при поиске и удалении, а результат вставки зависит от размера и может меняться из-за расширений,
распределения коллизий и работы сборщика мусора. По устройству обе очереди хранят ссылки в массиве,
а собственная хеш-таблица хранит два массива с запасом ячеек вместо отдельных объектов записей,
которые использует стандартная таблица. Память в байтах не замерялась, поэтому этот вывод касается
устройства структур, а не измеренного размера объектов.
