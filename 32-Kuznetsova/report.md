# Отчёт по ЛР2. Структуры данных

Кузнецова, группа ИУ3-32Б. Реализованы задачи 1A–1D, 2A–2D, 3A, 3B (24 балла).

## 1. Идея решения и выбор структур

**Очередь с приоритетом — двоичная куча в массиве.** Нужны `add`, `poll` и `peek` за логарифм, и куча даёт их без указателей: родитель и потомки находятся арифметикой по индексам, элементы лежат подряд (хорошо для кэша), а расширение массива вдвое даёт амортизированную стоимость. Порядок задаёт `Comparator`, поэтому один класс работает и как min-heap, и как max-heap (1B). `remove(T)` ищет элемент линейно, а затем возвращает на его место последний элемент и просеивает его вниз или вверх (1C). Конструктор из массива строит кучу методом Флойда: просеивание вниз от последнего внутреннего узла к корню (1D).

**Хеш-таблица — открытая адресация.** Все пары лежат в двух плоских массивах, без объектов-узлов, поэтому структура компактна и кэш-дружелюбна. Расплата — коллизии в одной общей последовательности проб. Для линейного пробирования смещение шага `i` равно `i`, для квадратичного — `i + 2i²` (почему именно так, см. `README.md`). Удаление ставит маркер `DELETED`, а перестройка (при превышении порога по живым парам с ростом ×2, по одним маркерам — без роста) их убирает.

**Применения.** `TopK` держит в min-куче k лучших элементов и вытесняет корень, если пришёл элемент лучше. `WordCounter` считает слова в `HashMapCustom`, а десять самых частых выбирает тем же `TopK`.

## 2. Асимптотика

Обозначения: n — число элементов, α — коэффициент загрузки.

### Куча

| Операция | Время | Обоснование |
|---|---|---|
| `add` | O(log n), амортизированно | `siftUp` поднимается не выше корня, то есть на ≤ log₂ n уровней; расширение массива O(n) происходит раз в n добавлений |
| `poll` | O(log n) | `siftDown` опускается не ниже листа: ≤ log₂ n уровней |
| `peek`, `size`, `isEmpty` | O(1) | чтение корня или поля |
| `remove(T)` | O(n) | поиск O(n), восстановление кучи O(log n) |
| `PriorityQueueCustom(T[])` | O(n) | на высоте h не более n/2^(h+1) узлов, и каждый опускается не более чем на h: сумма n·Σ h/2^(h+1) ≤ n |

Память O(n). Для `TopK`: время O(n log k), память O(k) — каждый из n элементов стоит одно сравнение с корнем и, если он лучше, операции за O(log k).

### Хеш-таблица

| Операция | Ожидаемое время | Худший случай |
|---|---|---|
| `put`, `get`, `containsKey`, `remove` | O(1) при α ≤ порога | O(n) при одинаковых хешах (см. 2C) |
| перестройка | O(n), но раз в n вставок, то есть амортизированно O(1) на вставку | |

Для линейного пробирования ожидаемое число проб при загрузке α: успешный поиск ≈ ½(1 + 1/(1−α)), неуспешный ≈ ½(1 + 1/(1−α)²). Поэтому порог загрузки напрямую влияет на скорость (замеры в `benchmarks.md`, раздел 2B). Память O(capacity) = O(n/α).

`WordCounter.countWords`: O(L) в среднем, где L — длина текста (каждое слово хешируется за время своей длины). `topWords`: плюс O(d log m), где d — число различных слов, m — сколько слов запрошено.

## 3. Ручные тесты и зачем они нужны

Ниже сценарии ручной проверки; все они также автоматизированы в тестах.

| Сценарий | Ожидание | Что ловит |
|---|---|---|
| Куча `[0, 10, 1, 11, 12, 2, 3]`, удалить `11` | куча остаётся корректной, порядок извлечения `0, 1, 2, 3, 10, 12` | заменяющий элемент (3) меньше родителя (10): без `siftUp` после `siftDown` куча ломается (`shouldSiftUpWhenReplacementIsSmallerThanParent`) |
| `remove` последнего элемента массива, корня, отсутствующего значения, из пустой очереди | `true`/`false` без исключений | граничные индексы при уменьшении `size` |
| `poll`/`peek` из пустой очереди | `NoSuchElementException` | требование задания |
| Три ключа с одним хешем, удалить средний | оставшиеся два находятся | маркер `DELETED` не рвёт цепочку проб |
| 100 000 раз «вставить и удалить» разные ключи | таблица не растёт, поиск не зацикливается | накопление `DELETED` и их вычистка перестройкой |
| Ключ с `hashCode() == Integer.MIN_VALUE` | работает | `Math.abs(Integer.MIN_VALUE) < 0` даёт отрицательный индекс |
| Порог 0.9, ёмкость 16, 14 ключей с одним хешем | все 14 находятся | последовательность проб обходит все ячейки (для квадратичного — проверка выбора `c2 = 2`) |
| 10 000 ключей `CollisionKey`: вставка, поиск, удаление | ничего не потеряно | корректность при полной деградации (2C) |
| Случайные 20 000 операций кучи и 50 000 операций таблицы против `java.util` | результаты совпадают с эталоном | случайные расхождения, которые руками не придумать |

Всего в модуле 92 теста: 31 на `PriorityQueueCustom`, по 18 на каждый способ пробирования, 8 на настройки таблицы, 9 на `TopK` и 8 на `WordCounter`.
