Обозначения: n — число входных элементов, k — размер Top-K, C — ёмкость таблицы,
α — доля живых ячеек, u — число уникальных ключей/элементов, L — длина текста,
w — число слов. Стоимость сравнения, equals/hashCode считается O(1), кроме явно

## 1A, 1B: бинарная куча

Высота полного бинарного дерева равна O(log(n+1)). Родитель узла i имеет индекс
(i−1)/2, дети — 2i+1 и 2i+2. `siftUp` за шаг переходит к родителю;
`siftDown` выбирает меньшего по компаратору ребёнка и переходит на уровень ниже.
Обе операции делают O(1) сравнений за уровень и используют O(1) временной памяти.

| Операция | Время | Дополнительная память операции |
|---|---|---|
| Пустой конструктор, в том числе с Comparator | O(1) | O(1) |
| add без расширения | O(log(n+1)) | O(1) |
| add с удвоением массива | O(n) в этом вызове | O(n) при копировании |
| add, амортизированная оценка | O(log(n+1)) | O(n) ёмкости структуры |
| poll | O(log(n+1)) | O(1) |
| peek, size, isEmpty | O(1) | O(1) |

Копирования при геометрическом росте суммарно стоят 16+32+…+2^p=O(n),
поэтому добавляют амортизированное O(1) к каждой вставке.
Строгая худшая O(log n) для каждого `add` несовместима с обычным расширением
одного динамического массива: единичный вызов с копированием занимает O(n).
В реализации и документации это различие указано явно.
Min-heap и max-heap меняют только знак порядка: оценки одинаковы.
Куча занимает O(n) памяти; после удалений массив не сжимается и занимает O(H),
где H — максимальная достигнутая ёмкость.

## 1D: построение bottom-up за O(n)

Листья не просеиваются. Начинаем с n/2−1 и идём к корню.
Узлов высоты h не больше n/2^(h+1); просеивание такого узла стоит O(h).
Суммарно:

```text
T(n) <= const * n * sum(h / 2^(h+1), h=0..∞) = O(n).
```

Чтение и копирование входных n элементов требует Ω(n), поэтому итог — Θ(n).
Память копии — O(n), временная память просеивания — O(1).
В отличие от этого, n последовательных `add` дают O(n log n) в худшем случае.
В тесте для 100 000 элементов дополнительно проверяется линейная граница числа сравнений.

## 2A, 2B: открытая адресация

Вычисляем `abs((long) hashCode) % C`. Long нужен до abs, поскольку
`abs(Integer.MIN_VALUE)` в int остаётся отрицательным.
Линейное пробирование посещает `(base+i) % C`.
Квадратичное посещает `(base+i+2i²) % C`; промежуточное вычисление выполняется в long.
Для степеней двойки остаток эквивалентен `& (C−1)`.

### Почему квадратичный обход полный

Пусть 0 <= i,j < C=2^p и f(i)=f(j) по модулю C, где f(x)=x+2x². Тогда

```text
f(i) − f(j) = (i−j) * (1+2(i+j)).
```

Второй множитель нечётный, поэтому взаимно прост с 2^p. Значит, C делит i−j;
при указанных границах это возможно только для i=j. Таким образом, все C индексов
различны. Сдвиг на base не меняет свойство, и свободная ячейка обязательно будет найдена.
Это важнее случайного выбора коэффициентов: пример c1=1,c2=3 из условия не является
обязательным и не гарантирует полный обход для степеней двойки.

### Время и память

| Метод | Ожидаемое время при равномерных хешах | Худший случай |
|---|---|---|
| Конструктор | O(1) | O(1) |
| get, containsKey, remove | O(1) | O(C) |
| put, без перехеширования | O(1) | O(C) |
| put, включая перехеширование | O(1) амортизированно | O(C+n²) |
| size, capacity, averageGetProbes, resetProbeStatistics | O(1) | O(1) |

При полном совпадении хешей вставка i-го ключа проверяет O(i) ячеек;
перехеширование n таких ключей требует 1+…+n=O(n²), плюс O(C) на выделение массивов.
Для линейного и квадратичного вариантов ожидаемые оценки предполагают достаточно
равномерные хеши. Защита от злонамеренных одинаковых hashCode не заявляется.

При α>0.75 массивы удваиваются. В отсутствие патологических коллизий
сумма стоимости расширений геометрическая и даёт O(1) амортизированно на вставку.
Маркеры считаются отдельно: живые элементы вместе с DELETED занимают не более 7/8 C
после вставки. Перед превышением этой границы маркеры очищаются при той же ёмкости.
После очистки живых элементов не более 3/4 C: до следующей очистки потребуется
как минимум порядка C/8 новых использованных ячеек. Поэтому стоимость O(C)
распределяется на Ω(C) операций и не превращает чередование удаления/вставки в O(C) на шаг.

Два массива, ключи и значения — O(C) ссылок; счётчики — O(1).
При перехешировании старые и новые массивы одновременно занимают O(C).
Удаление не уменьшает ёмкость, поэтому после удаления почти всех элементов
нельзя оценивать память как O(текущий n): она остаётся O(C).

## 3A: Top-K

Храним не более k кандидатов в min-heap. Если новый элемент больше минимума,
заменяем минимум. Инвариант: после каждого префикса куча содержит k наибольших
элементов этого префикса либо весь префикс, если элементов пока меньше k.
Поэтому после просмотра входа в куче находятся нужные элементы с сохранением повторов.

Обход через iterator занимает O(n), даже если input — связный список.
На один элемент приходится O(log(k+1)); извлечение k элементов — O(k log(k+1)).
При k<=n общая оценка O(n log(k+1)), для k>=2 это O(n log k), как в условии.
При k=1 время O(n), при k=0 метод возвращает пустой результат за O(1).
Дополнительная память кучи и результата — O(k+1). Результат идёт по убыванию:
минимумы записываются в массив с конца.

## 3B: частота слов

Проход нормализации регистра и выделение слов требуют O(L).
При хороших хешах каждый поиск/обновление таблицы — ожидаемо O(1) проб;
вычисление hashCode и сравнение строк в сумме учитываются их длинами.
Итоговое ожидаемое время — O(L), включая снимок ключей для Map-адаптера.
В патологическом случае коллизий оценка может достигать O(w*u*ℓmax + L),
где ℓmax — максимальная длина слова; константное время для строк не предполагается.

Дополнительная память — O(L+u): нормализованный текст, уникальные строки,
таблица и массив ключей. Строки уникальных слов суммарно имеют длину O(L).
Методы Map-адаптера: get/containsKey — ожидаемо O(1) проб таблицы,
size/isEmpty — O(1); containsValue/values/entrySet/hashCode/equals —
ожидаемо O(u) для ограниченной длины ключей.
`keySet` — O(1) на создание обёртки; поиск внутри представления Set линейный.
Сортировка u слов для вывода топ-10 выполняется только в бенчмарке: O(u log u),
не входит в время метода countWords и его замер.

## 3C: уникальные элементы

Однократно обходим список, проверяем собственную таблицу и сохраняем только
первое вхождение. Null отслеживается отдельным флагом. Результатный массив растёт
геометрически: сумма копирований O(u). Ожидаемое время — O(n), худшее O(n*u)
при массовых коллизиях (без учёта стоимости equals/hashCode).
Память свежей таблицы и результата — O(u+1). Входной список не копируется целиком.

## Собственные результаты List/Set

`ResultList.get/size/isEmpty` — O(1); indexOf/lastIndexOf/contains/equals/hashCode,
копирование в массив и subList — O(r), где r — число просмотренных/скопированных элементов.
Обычный итератор списка создаётся за O(1), переход — O(1).
`ResultSet` не хранит хеш-индекс: contains — O(r), iterator создаёт снимок за O(r).
Операции изменения неизменяемых результатов бросают UnsupportedOperationException за O(1).
Служебные контейнеры не участвуют в выборе Top-K или проверке уникальности:
в этих местах используются именно собственная куча и собственная хеш-таблица.
