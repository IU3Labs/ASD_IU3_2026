## 1. Идея решения и обоснование выбора структур данных

Реализации построены на массивах без использования стандартных коллекций в самих классах:

* **`PriorityQueueCustom<T>` (1A–1D)** — двоичная куча на массиве `Object[]` с индексами детей `2*i + 1`, `2*i + 2` и родителя `(i - 1) / 2`. Компаратор хранится всегда (при отсутствии подставляется естественный порядок), поэтому min- и max-куча работают на одном коде `siftUp` / `siftDown` со сдвигом элементов вместо обмена парами, а построение из массива (`1D`) идёт снизу вверх с `size / 2 - 1` до `0`.
* **`HashMapCustom<K, V>` (2A)** — открытая адресация с линейным пробированием `(index + 1) % capacity` и маркером `DELETED`, чтобы удаление не разрывало цепочку поиска. Коэффициент загрузки удерживается не выше `0.75` (удвоение ёмкости или перехеширование в ту же ёмкость для очистки маркеров).
* **`TopK.topK` (3A)** — min-куча `PriorityQueueCustom` размера не более `k`, где на вершине лежит худший из текущих `k` кандидатов.
* **`SlidingMinimum.slidingMin` (3D)** — min-куча пар `(value, index)` с ленивым удалением устаревших элементов (`index < i - k + 1`) перед снятием минимума для окна.

## 2. Анализ асимптотики (время и память)

### `PriorityQueueCustom<T>` (1A–1D)

| Операция | Время | Память |
|---|---|---|
| `peek()`, `size()`, `isEmpty()` | O(1) | O(1) |
| `add(T)` | O(log n) аморт. | O(n) всего |
| `poll()` | O(log n) | O(1) |
| `remove(T)` | O(n) | O(1) |
| Построение из массива (1D) | O(n) | O(n) |

### `HashMapCustom<K, V>` (2A)

| Операция | Среднее время | Худшее время |
|---|---|---|
| `put(K, V)` | O(1) аморт. | O(n) |
| `get(K)`, `containsKey(K)`, `remove(K)` | O(1) | O(n) |
| `size()`, `capacity()` | O(1) | O(1) |
| Перехеширование (`rehash`) | O(m) | O(m) |

По памяти для `HashMapCustom` требуется O(m), где m = capacity (m >= 4/3 * n при загрузке не выше 0.75).

### `TopK.topK` (3A) и `SlidingMinimum.slidingMin` (3D)

* **`TopK.topK` (3A):** время **O(n log k)**, дополнительная память — **O(k)**.
* **`SlidingMinimum.slidingMin` (3D):** время **O(n log n)**, дополнительная память — **O(n)** в худшем случае (на убывающем массиве старые элементы не вытесняются с вершины и накапливаются в куче).

## 3. Примеры ручных тестов и почему они важны

1. **Удаление элемента в середине цепочки линейного пробирования (`1`, `17`, `33` при ёмкости 16, удаление `17` и проверка `33`).** Показывает, что маркер `DELETED` сохраняет доступ к следующим элементам цепочки и не обрывает поиск раньше времени.
2. **Ключ с `Integer.MIN_VALUE` в `hashCode()`.** Проверяет защиту от отрицательного результата `Math.abs(Integer.MIN_VALUE)` и корректное приведение индекса в границы массива.
3. **Ключ с `null`-значением (`put("key", null)`).** Подтверждает, что `containsKey` отличает существующий ключ с `null`-значением от отсутствующего ключа.
4. **Удаление элемента из середины `PriorityQueueCustom` (`remove`).** Проверяет восстановление свойств кучи, когда перенесённый с конца элемент может нарушить порядок как вниз (`siftDown`), так и вверх (`siftUp`).
5. **`SlidingMinimum.slidingMin` на убывающем массиве.** Проверяет ленивое удаление устаревших индексов (`index < i - k + 1`) в неблагоприятном по накоплению элементов случае.
