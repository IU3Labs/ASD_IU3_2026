## Контракты и простые решения

**Очередь.** Меньший по компаратору элемент лежит в корне. `add` просеивает элемент вверх,
`poll` переносит последний элемент в корень и просеивает вниз. Размер массива при заполнении удваивается.
Без компаратора применяется естественный порядок; для max-heap передаётся `Comparator.reverseOrder()`.
`peek` и `poll` на пустой очереди бросают `NoSuchElementException`; `add(null)` запрещён.

**Таблица.** Ключи и значения лежат в двух параллельных массивах.
Начальный индекс — `Math.abs((long) key.hashCode()) % capacity`: приведение к long
сохраняет смысл формулы из задания и устраняет переполнение `abs(Integer.MIN_VALUE)`.
При коллизии проверяется следующая ячейка по кругу.
Удаление записывает `DELETED`, поэтому поиск продолжает проверять последующие ячейки.
Обновление существующего ключа не увеличивает размер и не вызывает расширение.
Перед вставкой нового ключа при превышении загрузки 0.75 ёмкость удваивается, живые записи перехешируются.
Ключи `null` запрещены; значения `null` разрешены. Отличить такой ключ от отсутствующего позволяет `containsKey`.
Ключи не должны менять `equals` и `hashCode`, пока находятся в таблице.

**Top-K.** Min-heap хранит не более k элементов. Если очередное значение больше минимума кучи,
заменяем минимум. Остальные значения пропускаем. В конце извлекаем результат по возрастанию.
Повторы сохраняются, вход не изменяется. `k = 0` даёт пустой результат без обхода входа,
`k > size` — все элементы, `k < 0` — `IllegalArgumentException`.
Ссылка на вход не может быть `null`; при обходе `null`-элементы отклоняются.

**Distinct.** Идём по входу и добавляем элемент в результат, только если его ещё нет в собственной таблице.
Сохраняется порядок первого появления. Вход не изменяется. `null`-вход и `null`-элементы запрещены.
Оба алгоритма обходят вход итератором, поэтому работают и со связными списками без индексного O(n²) обхода.

## Коллизии и деградация — задача 2C

`CollisionKey` сравнивает строки через `equals`, но всегда возвращает `hashCode() = 1`.
Поэтому разные ключи не смешиваются логически, но физически образуют одну длинную цепочку.
Для i-го нового ключа нужно проверить примерно i ячеек; сумма `1 + 2 + ... + n` даёт O(n²).
Серия поисков и удалений всех таких ключей также требует O(n²).
Перехеширование не устраняет искусственные коллизии: после изменения ёмкости хеши всё равно одинаковые.

Тест вставляет 10 000 таких ключей, проверяет значения по новым равным объектам,
удаляет чётные ключи, проверяет исчезновение чётных и сохранность нечётных, затем удаляет оставшиеся.
Отдельные тесты проверяют повторное использование DELETED и обновление ключа за удалённой ячейкой.
Замер того же пакета put/get/remove для обычных строк и CollisionKey приведён в `benchmarks.md`.
Результат на 10 000 ключах (среднее за 5 запусков после 3 прогревочных):

| Ключи | Время полного пакета, мс |
|---|---:|
| Обычные строки | 10.222 |
| CollisionKey | 1806.780 |

В этом запуске искусственные коллизии замедлили пакет примерно в 177 раз.
При повторном измерении времена и отношение могут измениться.
Большое замедление объясняется длиной цепочки, а не потерей данных.
Даже обычные строки `key-0`, `key-1`, ... дают кластеры: в простой таблице нет дополнительного перемешивания хеша.
Поэтому стандартный HashMap в этих замерах заметно быстрее; загрузка 0.75 сама по себе не исключает кластеры.

Маркеры DELETED не учитываются в числе живых записей. После множества удалений поиск может замедлиться,
даже если живых записей мало. Поиск ограничен `capacity` шагами и завершится даже при заполнении всех ячеек
маркерами; вставка повторно использует удалённую ячейку. Сжатие и очистка маркеров без расширения не реализованы.
