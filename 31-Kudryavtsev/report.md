## Идеи решений

Очередь построена как двоичная куча на массиве: это позволяет получать минимум за O(1)
и изменять очередь за O(log n) амортизированно. Компаратор меняет порядок, сохраняя тот же алгоритм.
Хеш-таблица использует линейное пробирование и два массива; DELETED сохраняет путь поиска после удаления.
Top-K поддерживает только k лучших кандидатов, а distinct использует таблицу для проверки уже встреченных значений.
Подробный расчёт времени и памяти вынесен в [asymptotics.md](asymptotics.md).

## Ручные примеры

| Проверка | Действия | Ожидаемый результат | Зачем нужна |
|---|---|---|---|
| Min-heap | add: 5, 1, 4, 2, 3; затем пять poll | 1, 2, 3, 4, 5 | Проверка обоих просеиваний |
| Max-heap | те же данные, reverseOrder | 5, 4, 3, 2, 1 | Работа компаратора |
| Пустая очередь | peek или poll | NoSuchElementException | Граничный случай |
| Повторы | add: 2, 2, 1; три poll | 1, 2, 2 | Повторы не теряются |
| Обновление | put(a, 7), put(a, 9) | get(a) = 9, size = 1 | Обновление не создаёт вторую запись |
| Удаление при коллизиях | put(A, 1), put(B, 2), remove(A), где хеши равны | get(B) = 2 | DELETED не обрывает поиск |
| Обновление за DELETED | предыдущий пример, затем put(B, 9) | get(B) = 9, size = 1 | Не вставляем дубликат в освободившуюся ячейку |
| Загрузка | 12 разных ключей, затем 13-й | capacity: 16 → 32 | Расширение только при превышении 0.75 |
| Top-K | [8, 1, 9, 3, 5], k = 3 | [5, 8, 9] | Замена минимума среди кандидатов |
| Top-K с повторами | [4, 1, 4, 4, 2], k = 3 | [4, 4, 4] | Учитываем вхождения, а не уникальные значения |
| Distinct | [3, 1, 3, 2, 1] | [3, 1, 2] | Сохраняем порядок первого вхождения |

## Автоматические проверки

`mvn clean test` в модуле: **79 тестов, 0 ошибок, 0 падений, 0 пропусков**.
Покрытие по JaCoCo: **100% строк и 100% ветвей** в коде решения, включая собственный итератор списка.
Для каждого пакета установлен обязательный порог покрытия строк 80%.
Бенчмарки лежат в тестовом дереве и не входят в эти проценты.
Проверена также сборка `mvn clean test` из корня всего репозитория:
родительский проект, пример и модуль ЛР2 завершились с BUILD SUCCESS.

Кроме конкретных примеров используются независимые эталоны:

- 20 000 смешанных операций очереди в каждом режиме сравниваются с java.util.PriorityQueue.
- 30 000 операций таблицы сравниваются с HashMap; проверяются все оставшиеся ключи.
- Top-K сравнивается с сортировкой для всех k на небольших случайных входах и для миллиона значений при k = 100.
- Distinct на 100 000 значений сравнивается с LinkedHashSet.
- 10 000 CollisionKey проходят вставку, проверку всех значений, частичное и полное удаление.
- Отдельно проверены отрицательные хеши, Integer.MIN_VALUE, переход через конец массива,
  перехеширование и завершение поиска в массиве, полностью заполненном DELETED.

## Эксперименты

[benchmarks.md](benchmarks.md) содержит фактически выполненные замеры:
основные структуры на 10 000 / 50 000 / 100 000 элементов и стандартные аналоги,
min-heap против max-heap на одном наборе из 100 000 элементов,
10 000 обычных и искусственно коллидирующих ключей,
Top-K на 1 000 000 значений, distinct против LinkedHashSet по времени и выделениям памяти.
Методика и ограничения измерений указаны непосредственно в файле замеров.

Реализация намеренно простая: без оптимизации хешей, очистки tombstone-маркеров и уменьшения массивов.
Наличие свободного места не исключает длинных цепочек пробирования, поэтому хеш-таблица
на выбранных строковых ключах уступает стандартной по скорости.
Куча и таблица сохраняют корректность во всех проверенных сценариях; совпадение с эталонами
и покрытие дополняют друг друга, но сами по себе не являются математическим доказательством.
