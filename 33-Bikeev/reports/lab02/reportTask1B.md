# Задача 1B. Min-heap и max-heap через компаратор

Лабораторная работа № 2.

Стоимость задачи: 2 балла.

## Условие

Реализовать очередь с приоритетом, конструктор которой принимает компаратор.
При отсутствии компаратора должен использоваться естественный порядок элементов.

Очередь должна поддерживать два режима:

- min-heap — первыми извлекаются минимальные элементы;
- max-heap — первыми извлекаются максимальные элементы.

В тестах необходимо продемонстрировать оба режима.
Дополнительно требуется сравнить их время работы на одном и том же наборе
из 100 000 случайных элементов и объяснить результат.

## Идея решения

Очередь хранит ссылку на компаратор в поле:

```java
private final Comparator<? super T> comparator;
```

Тип `Comparator<? super T>` позволяет передать как компаратор типа T,
так и компаратор подходящего базового типа.

Все сравнения элементов выполняются через один приватный метод `compare`.

Если компаратор передан, используется:

```text
comparator.compare(first, second)
```

Если компаратор равен null, используется естественный порядок:

```text
((Comparable<? super T>) first).compareTo(second)
```

Поэтому без компаратора элементы должны поддерживать согласованный естественный
порядок. При наличии подходящего компаратора элементы могут не реализовывать
интерфейс Comparable.

### Min-heap

Для чисел естественный порядок означает извлечение по неубыванию.

Очередь можно создать без явного компаратора:

```java
PriorityQueueCustom<Integer> minQueue = new PriorityQueueCustom<>();
```

Или передать компаратор естественного порядка:

```java
PriorityQueueCustom<Integer> minQueue =
        new PriorityQueueCustom<>(Comparator.naturalOrder());
```

Для чисел 4, 1, 7, 4 результат последовательных извлечений:

```text
1, 4, 4, 7
```

### Max-heap

Для извлечения чисел по невозрастанию передаётся обратный компаратор:

```java
PriorityQueueCustom<Integer> maxQueue =
        new PriorityQueueCustom<>(Comparator.reverseOrder());
```

Для чисел 4, 1, 7, 4 результат последовательных извлечений:

```text
7, 4, 4, 1
```

### Общие алгоритмы просеивания

Для обоих режимов сохраняется одно условие кучи:

```text
compare(parent, child) <= 0
```

Родитель должен находиться не позже своего ребёнка в порядке,
который задаёт выбранный компаратор.

При естественном порядке это означает, что родитель не больше ребёнка.
При обратном порядке чисел родитель, наоборот, не меньше ребёнка.

Методы siftUp и siftDown используют compare, поэтому отдельные реализации
просеивания для min-heap и max-heap не требуются.

### Элементы с равным приоритетом

Если компаратор возвращает 0, элементы имеют одинаковый приоритет.
При этом сами объекты могут быть различными.

Например, при сравнении строк только по длине строки cat и dog имеют
одинаковый приоритет. Очередь сохраняет обе строки.

Порядок извлечения элементов с одинаковым приоритетом не гарантируется.
Сохранение порядка их добавления в этой реализации не предусмотрено.

## Асимптотическая сложность

Обозначения:

- n — текущее количество элементов;
- C — ёмкость внутреннего массива.

В таблице предполагается, что одно сравнение элементов занимает O(1).

| Операция | Временная сложность |
|---|---|
| Создание пустой очереди с компаратором | O(1) |
| add без расширения массива | O(log n) |
| Отдельный add с расширением массива | O(n) |
| add с учётом амортизации расширений | O(log n) |
| poll | O(log n) |
| peek | O(1) |
| size | O(1) |
| isEmpty | O(1) |

Изменение направления сравнения не меняет высоту кучи и верхнюю оценку
числа уровней просеивания. При этом фактическое количество сравнений
и перемещений у min-heap и max-heap может различаться.

Полный цикл из n вставок в изначально пустую очередь и n извлечений
имеет верхнюю оценку O(n log n) в обоих режимах.

При расширении массива отдельная вставка требует O(n) времени на копирование.
Благодаря увеличению ёмкости в два раза суммарная стоимость копирований
на серии вставок линейна по количеству добавленных элементов.

Очередь хранит одну дополнительную ссылку на компаратор — это O(1) памяти
сверх внутреннего массива. Общая память очереди составляет O(C).
После удаления элементов ёмкость массива не уменьшается.

Просеивания выполняются итеративно и используют O(1) дополнительной памяти.
При расширении массива выделяется новый массив размером O(n).

Если сравнение элементов само требует времени f, стоимость сравнений
при просеивании составляет O(f log n). Поэтому для сложных пользовательских
компараторов время одного сравнения необходимо учитывать отдельно.

## Автоматические тесты

В классе PriorityQueueComparatorTest реализовано 6 тестов JUnit 5:

1. Явный Comparator.naturalOrder(): числа извлекаются по неубыванию.
2. Comparator.reverseOrder(): peek возвращает максимум,
   а извлечение выполняется по невозрастанию.
3. Компаратор null: используется естественный порядок элементов.
4. Пользовательский компаратор строк: сначала по длине, затем по алфавиту.
5. Объекты без Comparable: порядок задаётся переданным компаратором.
6. Разные элементы с одинаковым приоритетом: все элементы сохраняются.

В пятом тесте используются объекты Map.Entry<String, Integer>,
которые сравниваются по числовому значению.

В шестом тесте строки cat и dog сравниваются только по длине.
Тест проверяет наличие обеих строк после извлечения,
не требуя определённого порядка между ними.

Результат отдельного запуска класса тестов:
6 тестов выполнено, ошибок и неудачных проверок нет.

## Примеры для ручной проверки

| Настройка очереди и входные данные | Ожидаемый результат последовательных извлечений |
|---|---|
| Естественный порядок; 4, 1, 7, 4 | 1, 4, 4, 7 |
| Обратный порядок; 4, 1, 7, 4 | 7, 4, 4, 1 |
| Компаратор null; 9, -2, 3 | -2, 3, 9 |
| Строки по длине, затем по алфавиту; pear, a, fig, plum, kiwi | a, fig, kiwi, pear, plum |
| Строки только по длине; cat, dog, ox | Сначала ox, затем cat и dog в любом порядке |

Для max-heap после добавления чисел 4, 1, 7, 4 вызов peek должен вернуть 7.
Повторный вызов peek также должен вернуть 7, а size должен остаться равным 4.

## Сравнение производительности min-heap и max-heap

Измерение выполняет класс PriorityQueueBenchmark.

Для обоих режимов используется один и тот же массив
из 100 000 случайных значений Integer.

Генератор случайных чисел использует фиксированный seed 20261120.
Исходные данные и отсортированные эталоны создаются до начала измерений.

В сравнении участвуют:

- min-heap с Comparator.naturalOrder();
- max-heap с Comparator.reverseOrder().

Измеряется полный цикл:

1. Добавить все 100 000 элементов.
2. Извлечь все 100 000 элементов.

Создание пустой очереди и массива для результатов выполняется до запуска таймера.
Расширения внутреннего массива при добавлении элементов входят в измеряемое время.

Для каждого режима выполняется 5 прогревочных и 10 измеряемых запусков.
Запуски объединены в пары; порядок режимов в соседних парах чередуется.
Прогревочные результаты в среднее время не включаются.

После каждого запуска проверяются размер, пустота очереди
и вся последовательность извлечённых элементов.
Эти проверки выполняются после остановки таймера.

Фактические времена и параметры среды приведены в разделе
«Min-heap и max-heap: задача 1B» файла [benchmarks.md](benchmarks.md).
Исходные интервалы сохранены в [benchmark-samples.csv](benchmark-samples.csv).

### Объяснение результатов

Оба режима имеют одинаковую асимптотическую сложность,
но одинаковая асимптотика не означает одинаковое время в миллисекундах.

На одном и том же наборе чисел могут различаться количество сравнений,
число перемещений элементов и глубина отдельных просеиваний.
На измерения также влияют вызовы компаратора, оптимизации JVM,
сборка мусора и текущая нагрузка компьютера.

Поэтому результат сравнения относится к выбранным данным и среде запуска.
Он не доказывает, что один режим всегда быстрее другого.
Численные результаты конкретного запуска приведены в benchmarks.md.

## Вывод

Очередь поддерживает естественный и пользовательский порядок элементов.
Min-heap и max-heap используют одну реализацию и общие методы просеивания.
Направление извлечения определяется компаратором.

Корректность подтверждена шестью тестами:
проверены оба режима, компаратор null, пользовательские приоритеты,
элементы без Comparable и сохранение элементов с равным приоритетом.

Сравнение производительности выполнено на одинаковом наборе
из 100 000 случайных чисел. Результаты сохранены в benchmarks.md.
