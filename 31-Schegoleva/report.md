## 1. Идея решения и выбор структур данных

### 1A. `PriorityQueueCustom`: бинарная куча (min-heap) на массиве

Нужна очередь, у которой минимум достаётся за O(log n), а добавление не дороже. Бинарная куча хранится в обычном
массиве без указателей: родитель и дети находятся арифметикой индексов, поэтому нет накладных расходов на узлы и
хорошая локальность кэша. Инвариант: каждый элемент не больше своих детей. `add` ставит элемент в конец и поднимает
(`siftUp`), `poll` заменяет корень последним элементом и опускает его (`siftDown`). Массив удваивается, когда заполнен.
Освобождённая ячейка обнуляется, чтобы не держать ссылку на удалённый объект.

### 1C. `PriorityQueueCustom.remove(T)`: удаление по значению

Куча не умеет искать по значению (она упорядочена только «родитель не больше детей»), поэтому элемент ищется линейно
по массиву, O(n). Найденный элемент заменяется последним элементом кучи, после чего размер уменьшается. Перенесённый
элемент может оказаться больше новых детей (тогда он опускается) или меньше нового родителя (тогда он поднимается),
поэтому вызываются оба просеивания, и одно из них ничего не делает. Это O(log n), итого операция стоит O(n).
Удаляется первое вхождение; если элемент не найден или очередь пуста, возвращается `false`.

### 2A. `HashMapCustom`: открытая адресация с линейным пробированием

Ключи и значения лежат в двух массивах без цепочек, это экономнее по памяти и быстрее по кэшу, чем списки.
Коллизия разрешается переходом на следующую ячейку. При удалении ячейка помечается маркером `DELETED`, иначе
поиск по цепочке оборвался бы на удалённой ячейке и потерял бы ключи за ней. Загрузка (вместе с маркерами)
не превышает 0.75: так всегда остаются пустые ячейки, на которых останавливается поиск. При превышении ёмкость
удваивается с перехешированием. Если мешают только маркеры, а живых элементов мало, таблица перестраивается на
месте, иначе она растёт: это защищает от перестроек за O(n) на каждую пару `put`/`remove`.

### 3A. `TopK`: k наибольших элементов через кучу размера k

Полная сортировка стоит O(n log n), хотя нужны только k элементов. Мы держим min-heap из k лучших: его корень — самый
слабый из них. Новый элемент попадает в кучу, только если он больше этого корня, и вытесняет его. Время O(n log k),
память O(k). Используется собственная `PriorityQueueCustom` из задачи 1A.

### 3D. `SlidingMinimum`: минимум скользящего окна через кучу

В min-heap лежат пары (значение, индекс). Для каждой позиции окна нужен минимум только среди элементов окна, а куча
не умеет быстро удалять произвольный элемент. Поэтому устаревшие элементы (с индексом левее окна) удаляются лениво:
пока на вершине устаревший элемент, он извлекается. Когда на вершине элемент внутри окна, он и есть минимум окна:
все остальные элементы кучи не меньше него. Каждый элемент добавляется и удаляется не более одного раза, итого O(n log n).

## 2. Асимптотика (кратко)

| Структура / операция | Время | Память |
| --- | --- | --- |
| `PriorityQueueCustom.add` | O(log n) амортизированно | O(n) |
| `PriorityQueueCustom.poll` | O(log n) | |
| `PriorityQueueCustom.remove(T)` | O(n) | |
| `PriorityQueueCustom.peek`, `size`, `isEmpty` | O(1) | |
| `HashMapCustom.put/get/containsKey/remove` | O(1) в среднем, O(n) в худшем | O(n) |
| `TopK.topK` | O(n log k) | O(k) |
| `SlidingMinimum.slidingMin` | O(n log n) | O(n) |

Вывод формул и оценки числа проб (2.5 для успешного и 8.5 для неуспешного поиска при загрузке 0.75) — в `asymptotics.md`.

## 3. Ручные тесты и почему они важны

| Сценарий | Почему важен |
| --- | --- |
| Очередь: `poll`/`peek` на пустой очереди | Граничный случай: должна быть понятная ошибка, а не `ArrayIndexOutOfBounds` или `null` |
| Очередь: вход по возрастанию и по убыванию | Лучший и худший случаи для `siftUp`/`siftDown`, проверка, что порядок верен при любом входе |
| Очередь: начальная ёмкость 1 и 1000 элементов | Проверяет рост массива: ошибки копирования проявляются именно при расширении |
| Очередь: `remove` корня, элемента из середины и последнего элемента | Три разных ветки восстановления кучи: перенесённый элемент опускается, поднимается или не двигается |
| Очередь: `remove` несуществующего элемента, из пустой очереди и дубликата | Возврат `false` без побочных эффектов; удаляется только одно вхождение |
| Очередь: случайные `remove` против `ArrayList` | Эталонная модель проверяет, что после любых удалений порядок `poll` остаётся верным |
| Очередь: чередование `add` и `poll` | Реальная нагрузка; ловит ошибки, которые не видны при «сначала всё добавить, потом всё извлечь» |
| Окно: убывающий и возрастающий массив | Два крайних случая: при убывании устаревшие элементы копятся в куче, при возрастании минимум всегда на левом краю окна |
| Окно: размер 1, размер равен длине массива, окно больше массива, пустой массив | Граничные значения параметра `k` |
| Окно: 200 000 элементов, окно 1 000, против прямого перебора | Сценарий из задания; перебор O(n·k) даёт эталонный ответ |
| Таблица: ключи с одним хешем (`BadKey`) | Искусственно создаёт коллизии и проверяет цепочку пробирования |
| Таблица: удаление из середины цепочки | Главная ловушка открытой адресации: без маркера `DELETED` ключи за удалённой ячейкой «теряются» |
| Таблица: заворот цепочки через конец массива | Проверяет `% capacity` в пробировании |
| Таблица: `Integer.MIN_VALUE` и отрицательные хеши | `Math.abs(Integer.MIN_VALUE)` отрицателен, без обработки получился бы отрицательный индекс |
| Таблица: 100 000 пар `put`/`remove` | Проверяет, что маркеры не раздувают таблицу и поиск не зацикливается |
| Таблица: случайные операции против `java.util.HashMap` | Эталонная модель находит ошибки, которые не придумать вручную |
| Top-K: `k = 0`, `k > n`, `k = n`, пустой список | Граничные значения параметра |
| Top-K: дубликаты и одинаковые элементы | Результат — мультимножество: дубликаты считаются отдельно |
| Top-K: 1 000 000 элементов против сортировки | Проверка корректности и скорости на большом объёме |

## 4. Ограничения реализации

- `null`-ключи и `null`-элементы запрещены (`NullPointerException`), `null`-значения в таблице разрешены.
- Массивы структур не сжимаются после удалений.
- Очередь работает по естественному порядку `Comparable` (минимум первым), порядок через `Comparator` не поддерживается.
- Худший случай таблицы O(n) достигается только при массовых коллизиях хеша.
