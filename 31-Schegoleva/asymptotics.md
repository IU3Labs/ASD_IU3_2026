# Расчёт асимптотики (ЛР2)

Обозначения: `n` — число элементов в структуре, `k` — параметр Top-K, `C` — ёмкость массива,
`α = used / C` — коэффициент загрузки (учитываются живые элементы и маркеры `DELETED`).

---

## 1. `PriorityQueueCustom` (задача 1A, min-heap на массиве)

Куча хранится как полное бинарное дерево в массиве: дети узла `i` — `2i+1` и `2i+2`, родитель — `(i-1)/2`.
Высота такого дерева из `n` узлов равна `⌊log₂ n⌋`.

| Операция | Время | Обоснование |
| --- | --- | --- |
| `add` | O(log n) амортизированно | Элемент ставится в конец и всплывает (`siftUp`): на каждом уровне одно сравнение и одно перемещение, уровней не больше `⌊log₂ n⌋`. Расширение массива см. ниже |
| `poll` | O(log n) | Корень заменяется последним элементом, который тонет (`siftDown`): на каждом уровне до двух сравнений (выбор меньшего ребёнка и сравнение с ним), уровней не больше `⌊log₂ n⌋` |
| `peek` | O(1) | Минимум всегда в корне, `heap[0]` |
| `remove(T)` | O(n) | Линейный поиск первого вхождения по `equals`: до `n` сравнений. Затем последний элемент ставится на место удалённого и просеивается вниз и вверх: не более `⌊log₂ n⌋` уровней. Итого `O(n) + O(log n) = O(n)` |
| `size`, `isEmpty` | O(1) | Хранится счётчик `size` |

**Амортизированная стоимость расширения массива.** Массив удваивается, когда заполнен. Копирование при
удвоениях стоит `1 + 2 + 4 + … + n/2 < n` операций на `n` вставок, то есть O(1) на вставку. Поэтому
добавление остаётся O(log n) (в худшем случае одна вставка стоит O(n) на копирование).

**Память:** O(n). Массив никогда не сжимается, поэтому его размер не превышает `2·(максимальный размер за всё время)`.

## 2. `HashMapCustom` (задача 2A, открытая адресация, линейное пробирование)

Хеш: `Math.abs(key.hashCode()) % C` (для `Integer.MIN_VALUE`, где `abs` отрицателен, используется 0).
Коэффициент загрузки (с учётом `DELETED`) не превышает `0.75`, при превышении ёмкость удваивается.

**Среднее число проб (Д. Кнут, линейное пробирование, равномерное хеширование).**

- Успешный поиск: `½ · (1 + 1/(1 − α))`. При `α = 0.75` это `½ · (1 + 4) = 2.5` пробы.
- Неуспешный поиск (он же поиск места для вставки): `½ · (1 + 1/(1 − α)²)`. При `α = 0.75` это `½ · (1 + 16) = 8.5` пробы.

Так как `α ≤ 0.75` всегда, число проб ограничено константой, не зависящей от `n`.

| Операция | Среднее | Худшее | Обоснование |
| --- | --- | --- | --- |
| `put` | O(1) амортиз. | O(n) | Поиск ключа + вставка: константное число проб; худший случай — все ключи с одним хешем (одна длинная цепочка), либо вставка, вызывающая перестройку |
| `get`, `containsKey` | O(1) | O(n) | Константное среднее число проб; цикл поиска ограничен ёмкостью, поэтому завершается всегда |
| `remove` | O(1) | O(n) | Поиск + пометка ячейки маркером `DELETED` |
| `size`, `capacity` | O(1) | O(1) | Хранятся счётчики и длина массива |

**Амортизация перестроек.** Перестройка (`rehash`) стоит O(C).

- *Удвоение:* после него занято не более `0.75·C_старая` ячеек, а новый порог равен `1.5·C_старая`, то есть до
  следующей перестройки пройдёт не менее `0.75·C_старая = 0.375·C_новая` вставок. Стоимость O(C) делится на Ω(C)
  вставок, и это O(1) на вставку.
- *Перестройка на месте* (когда мешают маркеры `DELETED`) выполняется, только если живых элементов не больше
  половины порога, то есть между такими перестройками проходит не менее `0.375·C` вставок. Условие нужно намеренно:
  без него при размере таблицы вблизи порога пара `put`/`remove` вызывала бы перестройку за O(n) каждый раз.

**Память:** O(n): два массива (ключи и значения) длиной `C`. Ёмкость растёт только удвоением и подбирается так, что
`size > 0.375·C`, поэтому `C < 2.7·size` в момент роста, то есть `C = O(n_max)`, где `n_max` — максимальное число элементов
за всё время. Массивы не сжимаются, поэтому после массовых удалений ёмкость остаётся прежней.

## 3. `TopK.topK` (задача 3A, k наибольших элементов)

Алгоритм: куча (min-heap) размера не более `k`; корень — самый слабый из текущих `k` лучших.

- Для каждого из `n` элементов: сравнение с `peek()` — O(1); если элемент больше минимума, то `poll` и `add` — O(log k).
- В худшем случае (вход по возрастанию) заменяется каждый элемент: `n · O(log k)`.
- Извлечение результата: `k` вызовов `poll`, то есть `O(k log k)`.

**Итого: время O(n log k)**, при `k ≥ n` — O(n log n). Для случайного порядка входа ожидаемое число замен
около `k · ln(n/k)`, поэтому на практике время близко к O(n) (одно сравнение на элемент).

**Память:** O(k) дополнительно (куча); результат занимает O(min(k, n)). Входной список не изменяется.

Для сравнения, решение через полную сортировку: O(n log n) по времени и O(n) по памяти (копия списка).
При `k ≪ n` куча заметно выигрывает.

## 4. `SlidingMinimum.slidingMin` (задача 3D, минимум скользящего окна)

В `PriorityQueueCustom` лежат пары (значение, индекс). Элементы, вышедшие за левую границу окна, удаляются лениво:
только когда оказываются на вершине.

- Каждый из `n` элементов один раз добавляется: `O(log n)`.
- Каждый элемент извлекается не более одного раза: `O(log n)`. Всего извлечений не больше `n`.
- Чтение минимума окна `peek`: `O(1)`, выполняется `n − k + 1` раз.

**Итого: время O(n log n).**

**Память:** O(n) дополнительно (результат `n − k + 1` значений и куча). Куча в худшем случае хранит все `n` пар:
если массив убывает, новый элемент всегда меньше старых, поэтому устаревшие элементы остаются под ним и до вершины не
доходят. При возрастающем массиве куча, наоборот, остаётся размера около `k`.
