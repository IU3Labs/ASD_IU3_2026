# Отчёт по лабораторной работе № 2

## Задача 1A. Минимальная очередь с приоритетом

Реализована `PriorityQueueCustom<T>` на основе двоичной кучи, хранящейся в динамическом массиве.
При добавлении элемента используется `siftUp`, при извлечении корня — `siftDown`.
При заполнении массива его ёмкость удваивается. Операции `peek`, `size` и `isEmpty`
не изменяют структуру кучи.

Тестами проверены пустая очередь, одиночный элемент, дубликаты, отрицательные числа,
чередование вставок и извлечений, расширение массива и сравнение порядка извлечения
со стандартной `java.util.PriorityQueue` на 10 000 случайных чисел.

## Задача 1B. Компаратор

Конструктор с `Comparator<T>` позволяет использовать одну реализацию кучи
как min-heap и max-heap. Если компаратор не передан, используется естественный порядок.

Для одного набора из 100 000 случайных элементов измерено время операций `add + poll`:
22,859 мс для min-heap и 25,763 мс для max-heap. Оба режима имеют одинаковую
асимптотику; разница одного запуска не доказывает устойчивое преимущество min-heap.

## Задача 1C. Удаление по значению

Метод `remove(T item)` линейно ищет первое совпадение. Найденный элемент заменяется
последним элементом массива, после чего порядок кучи восстанавливается через
`siftUp` либо `siftDown`. Время поиска и удаления — `O(n)`.

### Примеры граничных случаев

- При элементах `1, 4, 2, 5` удаление `1` должно вернуть `true`; оставшиеся элементы
  извлекаются в порядке `2, 4, 5`. Этот случай проверяет удаление корня.
- При элементах `2, 2, 2` один вызов `remove(2)` должен уменьшить размер на единицу.
  Это проверяет удаление только одного вхождения.
- В пустой очереди `remove(1)` должен вернуть `false`.
  Этот случай проверяет обработку отсутствующего элемента.

Эти граничные случаи включены в автоматические проверки удаления.

## Задача 1D. Построение кучи за O(n)

Конструктор `PriorityQueueCustom(T[] array)` копирует переданный массив
и вызывает `siftDown` для внутренних узлов от последнего к корню.
Такое построение кучи требует `O(n)` времени и не изменяет исходный массив.

Для входного массива `8, 3, 5, 1` извлечения `poll()` дают `1, 3, 5, 8`.
Проверяются также отсутствие изменения исходного массива и пустой массив.

На 100 000 элементов последовательные вставки заняли 3,345 мс,
построение методом `heapify` — 2,438 мс. В данном запуске `heapify`
оказался быстрее приблизительно на 27,1%.

## Задача 2A. Хеш-таблица с линейным пробированием

Реализована `HashMapCustom<K, V>` с массивами ключей и значений.
При коллизии поиск свободной ячейки продолжается последовательно.
Удалённые элементы помечаются `DELETED`, чтобы сохранять цепочки пробирования.
При превышении порога заполнения 0,75 ёмкость увеличивается вдвое
с перехешированием элементов. Для минимального значения `hashCode()`
предусмотрена обработка переполнения при вычислении модуля.

Тестами проверены вставка и обновление значения, поиск, удаление, коллизии,
повторное использование удалённых ячеек, увеличение ёмкости и сравнение
со стандартной `java.util.HashMap` на случайных операциях.

На 100 000 элементов операции `put + get` заняли 15,675 мс для `HashMapCustom`
и 11,696 мс для `java.util.HashMap`. В данном запуске стандартная реализация
работала быстрее. Полные таблицы приведены в `benchmarks.md`.
