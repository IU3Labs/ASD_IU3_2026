# Расчёт асимптотики — ЛР2

Обозначения: `n` — число элементов в структуре, `c` — ёмкость массива, `L` — длина текста в символах,
`U` — число различных слов, `k` — сколько самых частых слов нужно вернуть.

## 1A. `PriorityQueueCustom<T>` — двоичная куча

Куча — это полное двоичное дерево, записанное в массив. На уровне `d` лежит не больше `2^d` узлов, поэтому при
`n` элементах высота дерева `h = ⌊log₂ n⌋`.

| Операция | Время | Обоснование |
|---|---|---|
| `add` | O(log n), амортизированно | `siftUp` поднимает элемент от листа к корню: не больше `h` шагов, на каждом одно сравнение с родителем. Расширение массива см. ниже. |
| `poll` | O(log n) | Последний элемент встаёт в корень, `siftDown` опускает его не больше чем на `h` уровней, на каждом до двух сравнений. |
| `peek` | O(1) | Минимум всегда лежит в `heap[0]`. |
| `size`, `isEmpty` | O(1) | Хранится счётчик `size`. |

**Расширение массива.** Когда массив заполнен, он копируется в новый, вдвое больший. Копирование стоит O(n), но
случается редко. За `n` вставок расширения произойдут при размерах 16, 32, 64, …, < 2n, и всего будет скопировано
`16 + 32 + … < 2n` элементов, то есть O(n) на все вставки. На одну вставку это O(1) амортизированно, поэтому
`add` в целом остаётся O(log n).

**Память:** O(n). Ёмкость массива не больше `max(16, 2n)`, дополнительной памяти операции не требуют, просеивание
работает на месте.

## 2A. `HashMapCustom<K, V>` — линейное пробирование

Начальная ячейка ключа вычисляется за O(1) по формуле `Math.abs(hashCode) % c`. Дальше идём по цепочке пробирования
до нужного ключа или до пустой ячейки. Стоимость операции равна числу просмотренных ячеек (проб).

**Почему в среднем O(1).** Пусть хеш-функция распределяет ключи равномерно и коэффициент заполнения равен `α`.
Тогда для линейного пробирования среднее число проб такое (Д. Кнут, «Искусство программирования», т. 3):

- успешный поиск: `½ · (1 + 1 / (1 − α))`;
- неуспешный поиск (и вставка нового ключа): `½ · (1 + 1 / (1 − α)²)`.

Таблица следит, чтобы `α ≤ 0,75` (в `α` входят и маркеры `DELETED`). Значит, успешный поиск в среднем делает не
больше `½ · (1 + 4) = 2,5` пробы, а неуспешный — не больше `½ · (1 + 16) = 8,5`. Это константы, не зависящие от `n`,
поэтому получаем O(1).

| Операция | Среднее | Худшее | Обоснование |
|---|---|---|---|
| `put` | O(1), амортизированно | O(n) | Поиск ключа, затем при необходимости перехеширование и вставка в первую свободную ячейку цепочки. |
| `get`, `getOrDefault`, `containsKey` | O(1) | O(n) | Поиск по цепочке до ключа или пустой ячейки. |
| `remove` | O(1) | O(n) | Поиск и запись маркера `DELETED`. |
| `size`, `isEmpty`, `capacity` | O(1) | O(1) | Хранятся в полях. |
| `forEach` | O(c) = O(n) | O(c) | Просмотр всех ячеек. |

**Худший случай O(n)** — когда хеш-коды всех ключей дают одну и ту же ячейку. Тогда все ключи выстраиваются в одну
цепочку, и её приходится просматривать целиком.

**Перехеширование** стоит O(c): каждый живой ключ переносится в новый массив. Ёмкость удваивается, когда живых
ключей становится больше `0,75 · c`. Как и в 1A, суммарная стоимость всех удвоений за `n` вставок равна O(n), то
есть O(1) на вставку амортизированно.

**Чистка маркеров `DELETED`.** Если порог 0,75 превышают в основном маркеры, а живых ключей не больше `0,375 · c`
(половина порога), таблица перехешируется с той же ёмкостью. Иначе ёмкость удваивается. В обоих случаях после
перехеширования живые ключи занимают не больше `0,375` новой ёмкости, а маркеров нет. Значит, до следующего
перехеширования должно пройти не меньше `0,375 · c` вставок или удалений, и стоимость O(c) делится между ними: O(1) на операцию амортизированно. Если бы
таблица, почти доверху заполненная живыми ключами, чистилась без удвоения, перехеширование за O(c) случалось бы
каждые несколько пар «удалить + вставить». Удвоение исключает этот случай.

**Память:** O(n). Сразу после удвоения заполнено не меньше `0,75 / 2 = 37,5 %` ячеек, значит `c ≤ n / 0,375 ≈ 2,7 n`
(для маленьких таблиц — не меньше начальной ёмкости 16). Используются два массива по `c` ссылок. Оценка
верна для `n`, равного наибольшему числу ключей, которое было в таблице: при удалениях таблица не уменьшается.

## 3B. Частота слов — `WordCounter`

| Шаг | Время | Память |
|---|---|---|
| Разбиение на слова (`WordTokenizer`) | O(L): один проход по строке, каждый символ обрабатывается за O(1) | O(длина самого длинного слова) на буфер |
| Подсчёт (`countWords`) | O(L) в среднем | O(U) на таблицу |
| Топ-k (`topWords`) | O(c + U · log k) | O(k) на кучу |
| **Итого** | **O(L + U · log k)**, при k = 10 это **O(L)** | **O(U)** |

Пояснения:
- Для каждого слова длины `|w|` выполняются `getOrDefault` и `put`. Вычисление `hashCode` и сравнение `equals`
  стоят O(|w|), а число проб в среднем O(1). Сумма длин всех слов не больше `L`, поэтому весь подсчёт занимает O(L).
- Для топ-k таблица обходится через `forEach` (O(c) = O(U)). Каждое слово кладётся в кучу размера не больше `k + 1`,
  а при переполнении «худшее» слово выбрасывается. И `add`, и `poll` стоят O(log k). В конце из кучи извлекаются
  `k` слов (O(k log k)) и разворачиваются (O(k)).
- Полная сортировка всех слов стоила бы O(U log U). Для k = 10 куча даёт O(U · log 10) = O(U).
