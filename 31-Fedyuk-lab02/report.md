Выбраны 1A, 1B, 1C, 1D, 2A, 2C, 3D: **2 + 2 + 2 + 2 + 3 + 3 + 2 = 16 баллов**.
Основной код реализует структуры самостоятельно на массивах; стандартные коллекции
используются только в тестовом дереве для эталонных ответов и измерений.

## 1A. Очередь с приоритетом

Двоичная куча хранится в Object[]. Дети элемента i имеют индексы 2i + 1 и 2i + 2,
родитель — (i − 1) / 2. Добавленный элемент просеивается вверх, замена корня после
извлечения — вниз. При заполнении массива ёмкость удваивается. Освобождённые ссылки
обнуляются. Пустые peek и poll бросают NoSuchElementException.

Пример: добавить 7, −3, 4, 0, 2; последовательные poll дают −3, 0, 2, 4, 7.
В тестах также проверены пустая очередь, повторяющиеся значения, края int и рост до 100 000 элементов.

## 1B. Компаратор

Comparator задаёт приоритет, без него используется Comparable. Поэтому один и тот же
код работает как min-heap и max-heap. Например, для 1, 8, −2 обратный компаратор даёт
8, 1, −2. Есть проверка объектов int[], не реализующих Comparable, с внешним компаратором.
Замеры обоих режимов на одном наборе 100 000 значений приведены в benchmarks.md.

## 1C. Удаление значения

Линейным просмотром находится первое совпадение по equals. На его место ставится
последний элемент. Если он меньше родителя, запускается siftUp, иначе siftDown.
Это важно: только просеивания вниз недостаточно при удалении из середины.

Проверены удаление корня, середины с обоими направлениями восстановления, последнего
элемента, одного из дубликатов, отсутствующего значения и удаление из пустой очереди.
Время O(n), поскольку поиск линейный, а восстановление занимает O(log n).

## 1D. Построение кучи

Конструктор копирует массив и просеивает внутренние узлы от n/2 − 1 к нулю.
Большинство узлов близки к листьям и требуют мало работы; сумма затрат составляет O(n).
Исходный массив не меняется и не используется как внутреннее хранилище.
Конструктор и последовательные add сравнены на 100 000 элементов.

## 2A. Хеш-таблица

В двух массивах хранятся ключи и значения. Индекс вычисляется по формуле задания,
с приведением hashCode к long перед abs. Коллизии разрешаются поиском следующей
ячейки по кругу. При превышении 0.75 ёмкость удваивается и записи переносятся заново.
Удаление оставляет DELETED, чтобы следующий ключ в цепочке оставался доступным.
Накопившиеся маркеры удалений периодически очищаются без роста ёмкости.

Пример: put("x", 1), put("x", 2) оставляет одну запись со значением 2.
Отдельно проверяются null-значения, одинаковые по equals ключи, переход через конец
массива, Integer.MIN_VALUE в hashCode, массовые расширения и очистка DELETED.

## 2C. Коллизии

CollisionKey хранит строку, сравнивается по её содержимому и всегда возвращает хеш 7.
В отдельном тесте вставлены и найдены 10 000 разных ключей. После удаления всех
чётных ключей проверено отсутствие удалённых и сохранность нечётных, затем удалены остальные.
В конце размер равен нулю, поиск отсутствующего ключа корректно завершается.
Замеры демонстрируют ухудшение скорости; объяснение есть также в README.md.

## 3D. Скользящий минимум

В собственной очереди хранятся пары (значение, индекс). Сначала добавляется очередной
элемент, затем из корня удаляются записи левее текущего окна. Корень содержит минимум
допустимых элементов. Старые записи глубже в куче удаляются позже, когда дойдут до корня.

Пример: [1, 3, −1, −3, 5, 3, 6, 7], k = 3 → [−1, −3, −3, −3, 3, 3].
Есть сравнение с полным перебором на 300 малых случайных массивах и независимой
монотонной очередью на массиве 200 000 элементов с окном 1000. Время O(n log n), память O(n).
