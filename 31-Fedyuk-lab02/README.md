## Почему коллизии замедляют таблицу

У CollisionKey все строки имеют один hashCode, но equals различает их по содержимому.
Каждая новая запись ищет свободное место в общей цепочке; поиск тоже может просмотреть
почти все ключи. Поэтому один поиск вместо ожидаемого O(1) становится O(n), а набор
из n поисков — O(n²). Маркер DELETED сохраняет доступ к элементам после удалённых
ячеек; он влияет на скорость, но не должен приводить к потере данных.

В измерении 10 000 поисков собственная таблица показала 0.412 мс для обычных строк
и 232.356 мс для CollisionKey. Тип ключа тоже меняется, поэтому точный коэффициент
относится к этим двум наборам. В тесте вставлены, найдены и удалены все 10 000 ключей.

## Принятые соглашения

- Очередь не принимает null; `peek` и `poll` на пустой очереди бросают NoSuchElementException.
- Без компаратора элементы должны поддерживать Comparable; с компаратором это не требуется.
- `remove` в очереди удаляет первое равное значение при просмотре внутреннего массива,
  а не обязательно самое раннее по времени добавления.
- Таблица не принимает null-ключи, но допускает null-значения. Наличие ключа проверяется через containsKey.
- Хеш вычисляется как `Math.abs((long) key.hashCode()) % capacity`: приведение к long
  сохраняет смысл формулы задания и корректно обрабатывает Integer.MIN_VALUE.
- Загрузка живыми записями не превышает 0.75. При накоплении более 7/8 занятых или
  удалённых ячеек таблица очищается перехешированием без роста ёмкости.
- Для окна требуется `1 ≤ k ≤ n`; null и недопустимые размеры явно отклоняются.
