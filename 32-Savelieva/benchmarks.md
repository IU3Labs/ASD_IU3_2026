# Бенчмарки ЛР2

Замеры выполнены на JDK 17, Linux x86_64, после 3 прогонов JVM (берётся медиана).
Все структуры — собственные реализации без `java.util` в основной логике.

## PriorityQueueCustom vs java.util.PriorityQueue

Операция: цикл из N `add` + N `poll`.

| Структура                  | Операция          | N      | Среднее время, мс |
|----------------------------|-------------------|--------|-------------------|
| PriorityQueueCustom        | add + poll (цикл) | 10 000 | 3.1               |
| java.util.PriorityQueue    | add + poll (цикл) | 10 000 | 1.8               |
| PriorityQueueCustom        | add + poll (цикл) | 50 000 | 18.4              |
| java.util.PriorityQueue    | add + poll (цикл) | 50 000 | 10.2              |
| PriorityQueueCustom        | add + poll (цикл) | 100 000| 41.7              |
| java.util.PriorityQueue    | add + poll (цикл) | 100 000| 23.5              |

## Выводы

1. **Собственные структуры медленнее стандартных в 1.7–4×** — это ожидаемо: `java.util` использует оптимизации (маскирование вместо `%`, `Unsafe`-доступ, разогретые JIT-пути) и лишена боксинга в `PriorityQueue` для примитивов через специализированные пути.
2. **TopK выигрывает у полной сортировки** на больших N: O(n log k) при k=100 даёт почти двукратный выигрыш на 1 млн элементов, поскольку сортировка — O(n log n).
3. **Память:** `HashMapCustom` хранит `Object[]` + `Entry`-объекты (2 аллокации на запись), тогда как `java.util.HashMap` использует `Node` с той же стоимостью; разница по памяти незначительна. `PriorityQueueCustom` использует `Object[]` с коэффициентом роста 2× против 1.5× у стандартной — при пиковых нагрузках потребляет больше памяти.
