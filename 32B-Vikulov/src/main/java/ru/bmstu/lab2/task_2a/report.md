# Задача 2A. Хеш-таблица с линейным пробированием

**Студент:** Викулов Петр, ИУ3-32Б · **ЛР 2** · **Баллы:** 3 ·
**Решение:** [`HashMapCustom.java`](HashMapCustom.java) ·
**Тесты:** [`HashMapCustomTest.java`](../../../../../../test/java/ru/bmstu/lab2/task_2a/HashMapCustomTest.java)

## Условие

Реализовать `HashMapCustom<K, V>` с линейным пробированием: `put`, `get`, `containsKey`, `remove`, `size`,
`capacity`. Хеш-функция `Math.abs(key.hashCode()) % capacity`. Коэффициент загрузки не более 0.75, при
превышении — удвоение ёмкости с перехешированием. Для удалённых ячеек — маркер `DELETED`.

## Устройство

Открытая адресация: все пары лежат прямо в массивах, без списков и узлов.

```
keys:   [ null | "b" | DELETED | "a" | "c" | null | ... ]
values: [ null |  2  |  null   |  1  |  3  | null | ... ]
```

- `keys[i]` и `values[i]` — параллельные массивы: ключ и его значение лежат под одним индексом.
- Ячейка ключа бывает **пустой** (`null`, в неё никогда ничего не клали), **удалённой** (`DELETED`) или
  **занятой**.
- **Поиск ключа** ([`findIndex`](HashMapCustom.java#L174-L188)): начинаем с домашней ячейки
  `|hashCode % capacity|` и идём вправо по кругу (`index + 1`), пока не найдём ключ или не упрёмся
  в пустую ячейку. Пустая ячейка означает «ключа нет»: при вставке он лёг бы не дальше неё.
- **Вставка** ([`put`](HashMapCustom.java#L69-L78)): если ключ есть — обновляем значение; если нет — кладём
  в первую пустую **или удалённую** ячейку цепочки ([`insertAbsent`](HashMapCustom.java#L191-L202)).
- **Удаление** ([`remove`](HashMapCustom.java#L110-L120)) ставит маркер `DELETED`, а не `null`.

### Зачем маркер `DELETED`

Ключи `a`, `b`, `c` с одинаковой домашней ячейкой 3 лежат цепочкой в ячейках 3, 4, 5. Если при удалении `b`
записать в ячейку 4 `null`, поиск `c` начнётся с 3, дойдёт до пустой 4 и остановится — `c` «потеряется».
`DELETED` говорит поиску «здесь было занято, иди дальше», а вставке — «сюда можно положить новый ключ».
Это проверяет тест `shouldFindKeyAfterRemovingEarlierKeyInSameProbeChain`.

### Загрузка и ресайз

Поле `size` — число живых элементов, `occupied` — число непустых ячеек (живые + `DELETED`). Перед вставкой
нового ключа [`ensureRoomForInsert`](HashMapCustom.java#L209-L216) проверяет, что после неё
`occupied ≤ 0.75 · capacity`. Если нет:

- живых элементов много (`size + 1 > 0.75 · capacity`) — ёмкость **удваивается**;
- иначе порог превышен из-за маркеров `DELETED` — таблица **перестраивается в той же ёмкости**: маркеры
  исчезают, а размер не растёт.

Почему считается именно `occupied`, а не `size`: маркеры, как и живые ключи, удлиняют цепочки пробирования.
Без их учёта таблица после множества вставок и удалений могла бы заполниться одними `DELETED`, не имея ни
одной пустой ячейки, и поиск отсутствующего ключа обходил бы её целиком. Тест
`shouldNotGrowForeverUnderInsertRemoveChurn` делает 100 000 пар вставка/удаление и проверяет, что ёмкость
осталась 16.

Благодаря порогу в таблице **всегда есть пустая ячейка**, поэтому цикл в `insertAbsent` гарантированно
завершается, а `findIndex` в норме выходит по пустой ячейке. Ограничение «не больше `capacity` шагов» в
строке 177 — страховка.

### Хеш-функция и `Integer.MIN_VALUE`

[`indexFor`](HashMapCustom.java#L169-L171) считает `Math.abs(key.hashCode() % capacity)` — модуль берётся
**после** остатка, а не до, как в формуле из условия. Причина: `Math.abs(Integer.MIN_VALUE)` в Java равен
`Integer.MIN_VALUE` (модуль `2³¹` не помещается в `int`), и индекс получился бы отрицательным. Остаток же по
модулю всегда меньше ёмкости, так что его модуль безопасен. Для всех остальных хешей результат совпадает с
формулой из условия. Проверяет тест `shouldHandleNegativeAndMinValueHashCodes`.

### Прочие решения

- **`null`-ключ запрещён** (`NullPointerException`): у `null` нет `hashCode()`, а `null` в массиве ключей уже
  означает «пустая ячейка».
- **`null`-значение разрешено**; отличить его от отсутствующего ключа можно через `containsKey`.
- `forEach` обходит пары в порядке ячеек — он нужен задачам 3B и 3C, которым надо пройти по всей таблице.

## Асимптотика

`n` — число элементов, `m` — ёмкость, `α = n / m ≤ 0.75` — коэффициент загрузки.

| Операция | Время | Определяющие строки |
|----------|-------|---------------------|
| `get`, `containsKey`, `remove` | O(1) в среднем, O(n) в худшем | цикл пробирования [`findIndex` L177–L186](HashMapCustom.java#L177-L186) |
| `put` | O(1) амортизированно в среднем, O(n) в худшем | `findIndex` + [`insertAbsent` L193–L195](HashMapCustom.java#L193-L195) + редкий `rehash` |
| `size`, `isEmpty`, `capacity` | O(1) | [L128](HashMapCustom.java#L128), [L137](HashMapCustom.java#L137), [L146](HashMapCustom.java#L146) |
| `forEach` | O(m) | [цикл L157–L161](HashMapCustom.java#L157-L161) |
| `rehash` | O(m) | [цикл L226–L230](HashMapCustom.java#L226-L230) |

**Почему в среднем O(1).** Тело цикла в `findIndex` (строки 178–185) стоит O(1), а число итераций равно
длине цепочки от домашней ячейки до искомого ключа или первой пустой ячейки. При равномерном хеше ожидаемая
длина для линейного пробирования (оценка Кнута) — около `½(1 + 1/(1 − α))` для успешного поиска и
`½(1 + 1/(1 − α)²)` для неуспешного. При `α ≤ 0.75` это не больше 2.5 и 8.5 проб — константы, не зависящие
от `n`.

**Почему в худшем O(n).** Если все ключи попали в одну цепочку (одинаковый хеш или плотный кластер), поиск
проходит её целиком. Эксперимент `ClusteringDemo` (см. [`benchmarks.md`](../../../../../../../lab2/benchmarks.md))
показывает это на плотных ключах.

**Почему `put` амортизированно O(1).** Удвоение (`rehash`, строки 226–230) стоит O(m), но происходит, только
когда число элементов выросло до `0.75·m` с `0.375·m` (после прошлого удвоения). Значит, между двумя
удвоениями было не меньше `0.375·m` вставок, и на каждую приходится O(1) работы ресайза. Перестройка в той же
ёмкости из-за `DELETED` аналогично оплачивается удалениями, которые эти маркеры создали.

**Память:** два массива по `m` ссылок, `m < n / 0.375` — то есть O(n).
