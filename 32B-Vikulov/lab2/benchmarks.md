# Бенчмарки — ЛР 2

**Студент:** Викулов Петр, ИУ3-32Б

## Условия замеров

- Машина: облачный контейнер, Intel Xeon 2.1 ГГц, 4 ядра; OpenJDK 21, куча `-Xms1g -Xmx1g`.
- Методика ([`Bench.java`](../src/test/java/ru/bmstu/lab2/bench/Bench.java)): сначала прогрев не меньше 0,5 с,
  чтобы JIT-компилятор успел скомпилировать горячий код, затем среднее по 20 запускам (`System.nanoTime`).
  Если для замера нужно свежее состояние (например, заполненная таблица перед `remove`), оно готовится
  **вне** замера времени.
- Каждая программа-бенчмарк запускается в отдельной JVM. Время — на всю серию из N операций, а не на одну.
- Абсолютные числа зависят от машины. Значение имеет соотношение между реализациями и рост с N.

Как воспроизвести (из корня репозитория; на Windows разделитель classpath `;` вместо `:`):

```bash
mvn -pl 32B-Vikulov -am test-compile
CP=32B-Vikulov/target/classes:32B-Vikulov/target/test-classes
java -Xms1g -Xmx1g -cp $CP ru.bmstu.lab2.bench.HashMapBenchmark
java -Xms1g -Xmx1g -cp $CP ru.bmstu.lab2.bench.DistinctBenchmark
java -Xms1g -Xmx1g -cp $CP ru.bmstu.lab2.bench.ClusteringDemo
java -Xms1g -Xmx1g -cp $CP ru.bmstu.lab2.bench.WordFrequencyDemo book.txt book.txt
```

## 1. `HashMapCustom` (2A) против `java.util.HashMap`

[`HashMapBenchmark`](../src/test/java/ru/bmstu/lab2/bench/HashMapBenchmark.java): N различных случайных ключей
`Integer` по всему диапазону `int`. Операции: N вставок в пустую таблицу (с ростом ёмкости от 16),
N успешных поисков, N удалений из заполненной таблицы.

| Структура | Операция | N элементов | Среднее время (мс) | Примечание |
|---|---|---|---|---|
| `HashMapCustom` | put | 10 000 | 0.63 | ёмкость 16 384 |
| `java.util.HashMap` | put | 10 000 | 0.32 | |
| `HashMapCustom` | get | 10 000 | 0.14 | |
| `java.util.HashMap` | get | 10 000 | 0.02 | |
| `HashMapCustom` | remove | 10 000 | 0.15 | |
| `java.util.HashMap` | remove | 10 000 | 0.06 | |
| `HashMapCustom` | put | 50 000 | 5.27 | ёмкость 131 072 |
| `java.util.HashMap` | put | 50 000 | 4.83 | |
| `HashMapCustom` | get | 50 000 | 0.66 | |
| `java.util.HashMap` | get | 50 000 | 0.53 | |
| `HashMapCustom` | remove | 50 000 | 0.97 | |
| `java.util.HashMap` | remove | 50 000 | 0.69 | |
| `HashMapCustom` | put | 100 000 | 16.32 | ёмкость 262 144 |
| `java.util.HashMap` | put | 100 000 | 14.26 | |
| `HashMapCustom` | get | 100 000 | 2.13 | |
| `java.util.HashMap` | get | 100 000 | 1.21 | |
| `HashMapCustom` | remove | 100 000 | 3.16 | |
| `java.util.HashMap` | remove | 100 000 | 1.54 | |

Время растёт с N примерно линейно (O(1) на операцию). Скачки сверх линейного (например, `put` 50 000 → 100 000
дал рост в 3 раза) объясняются тем, что таблица перестаёт помещаться в кеш процессора, а не асимптотикой —
то же видно и у `java.util.HashMap`.

## 2. `Distinct` (3C) против `new LinkedHashSet<>(items)`

[`DistinctBenchmark`](../src/test/java/ru/bmstu/lab2/bench/DistinctBenchmark.java): N случайных чисел из
диапазона `[0, N/2)` — около 43 % уникальных. Память — прирост занятой кучи после сборки мусора, пока
структура удерживается ссылкой. Для `Distinct` суммируются внутренняя таблица `seen` и список-результат:
во время работы существуют оба. Для N = 10 000 точность замера памяти невысокая (порядка десятков КБ).

| Реализация | N элементов | Уникальных | Среднее время (мс) | Пиковая память (КБ) |
|---|---|---|---|---|
| `Distinct.distinct` | 10 000 | 4 352 | 2.75 | 89 |
| `new LinkedHashSet<>(items)` | 10 000 | 4 352 | 0.23 | 234 |
| `Distinct.distinct` | 50 000 | 21 615 | 2.57 | 380 |
| `new LinkedHashSet<>(items)` | 50 000 | 21 615 | 1.44 | 1 868 |
| `Distinct.distinct` | 100 000 | 43 164 | 6.21 | 697 |
| `new LinkedHashSet<>(items)` | 100 000 | 43 164 | 3.36 | 3 735 |
| `Distinct.distinct` | 1 000 000 | 432 281 | 106.75 | 13 312 |
| `new LinkedHashSet<>(items)` | 1 000 000 | 432 281 | 81.62 | 26 121 |

Время `Distinct` при N = 10 000 (2,75 мс) **не меньше, чем при N = 50 000** (2,57 мс), хотя элементов
в 5 раз меньше. Это не ошибка замера: причина разобрана в следующем разделе.

## 3. Эксперимент: кластеризация при линейном пробировании

[`ClusteringDemo`](../src/test/java/ru/bmstu/lab2/bench/ClusteringDemo.java): на сколько ячеек ключ сдвинут
от своей домашней ячейки `|hash % capacity|` после вставки. Ключи — такие же, как во входе `DistinctBenchmark`
(«плотные»), и для сравнения случайные по всему `int`.

| Ключи | N | Уникальных | Ёмкость | Среднее смещение | Макс. смещение |
|---|---|---|---|---|---|
| плотные [0, N/2) | 10 000 | 4 352 | 8 192 | **34.3** | **1 422** |
| случайные `int` | 10 000 | 10 000 | 16 384 | 2.4 | 72 |
| плотные [0, N/2) | 50 000 | 21 615 | 32 768 | 3.3 | 712 |
| случайные `int` | 50 000 | 49 999 | 131 072 | 2.7 | 122 |

У `Integer` хеш равен самому числу. Плотные ключи `0…4999` при ёмкости 4096 (перед последним удвоением)
ложатся в ячейки подряд, а ключи `4096…4999` по модулю попадают в ячейки `0…903`, **уже** занятые ключами
`0…903`. Возникают длинные сплошные кластеры, и ключу приходится пробовать в среднем 34 ячейки вместо 2–3.
При N = 50 000 диапазон ключей (25 000) меньше ёмкости (32 768), ключи «не заворачиваются», и кластеров почти
нет. Это **первичная кластеризация** — известный недостаток линейного пробирования. Формула хеш-функции
задана условием, поэтому она не менялась. `java.util.HashMap` от этого защищён: он перемешивает старшие биты
хеша с младшими (`h ^ (h >>> 16)`) и хранит коллизии в отдельных цепочках, а не в соседних ячейках.

## Выводы

`HashMapCustom` медленнее `java.util.HashMap` в 1,1–2 раза на N от 50 000 и до 7 раз на N = 10 000, где
стандартная таблица целиком помещается в кеш процессора и выигрывает за счёт микрооптимизаций. На скорость
повлияли деление `%` вместо побитового `&` (у `HashMap` ёмкость — степень двойки), отсутствие перемешивания
битов хеша, из-за которого на плотных ключах возникает кластеризация (раздел 3), и двойной поиск в `Distinct`
(`containsKey`, затем `put`). По памяти открытая адресация, наоборот, выигрывает в 2–5 раз: на элемент
приходятся только ячейки массивов, а `HashMap` и `LinkedHashSet` создают на каждый элемент отдельный
объект-узел примерно в 32–40 байт.
